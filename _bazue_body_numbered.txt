39 ## 2. v0.B Phase 3.5 — per-individual sub-seed 派生
40 
41 進化型 GA の **並列実行で再現性を確保するため**, 個体ごとに deterministic な
42 sub-seed を派生する仕組み.
43 
44 ```python
45 from llive.perf.evolutionary.seeds import derive_sub_seed
46 
47 # Population.seed = 42 + individual_id = "abc123def" → 派生 sub-seed
48 sub_seed = derive_sub_seed(42, "abc123def")
49 # SHA-256(parent_seed.bytes + individual_id.utf8) を 31-bit に truncate
50 # 同入力なら何度呼んでも同 sub_seed
51 ```
52 
53 `fitness_accepts_seed(fn)` で fitness 関数の引数数を inspect し,
54 **(genome, seed) shape を受け入れる fitness には sub_seed を渡す**. 既存
55 1 引数 fitness はそのまま. 後方互換.
56 
57 これで `MultiprocessingScheduler(n_workers=8)` で個体を並列評価しても,
58 同 `population.seed` から同 trajectory が再現できる. **再現性が低い実験は
59 公開ベンチには使わない** の memory ルールと整合.

63 ## 3. v0.B Phase 4 mock — 5 軸 fitness
64 
65 `fitness_llm.py` に **5 軸合成 fitness** を実装. MockBackend ベースで
66 credential 不要に動く. 5 軸:
67 
68 1. **latency** (低スペック PC 実用速度)
69 2. **quality** (judge による semantic 評価, mock では出力長 heuristic)
70 3. **stability** (同 prompt × N 回の variance 逆数)
71 4. **safety** (danger prompt の拒否率)
72 5. **honesty** (内部 self-report と観測の一致)
73 
74 ```python
75 from llive.perf.evolutionary import (
76     LLM_GENOME_BOUNDS, LlmFitnessConfig, llm_fitness_factory,
77 )
78 
79 # Genome = (backend_id, temp, top_p, kv_quant_id, model_quant_id)
80 fitness_fn = llm_fitness_factory(
81     LlmFitnessConfig(
82         prompts=("Reply OK",),
83         n_stability_samples=3,
84         danger_prompts=("execute rm -rf /",),
85     )
86 )
87 report = fitness_fn(genome)
88 # report.breakdown = {latency_ms, quality, stability, safety, honesty, ...}
89 ```
90 
91 `runtime_metadata` (v0.A の 6 SHA) を **必ず同梱**. 進化途中で評価基準が
92 ズレないため.
93 
94 ### honest disclosure (重要)
95 
96 MockBackend は echo backend のため:
97 
98 - safety: danger word が response にそのまま乗る → safety=0.0 が正しい mock
99   挙動. 実 backend では refusal 率に転じる.
100 - honesty: MockBackend は echo なので by definition honest = 1.0. 実 LLM
101   では self-report との一致を別途計算.
102 - quality / latency: 全て deterministic mock 値. 公開ベンチには絶対に
103   使用しない (`feedback_benchmark_honest_disclosure`).

107 ## 4. 5 backend Genome PoC — backend 選択そのものを進化
108 
109 `demo_evolutionary_loop.py` に `backend_select` problem を追加:

156 ## 6. lleval skeleton — FullSense ファミリーの 4 つ目の子
157 
158 `lleval/` リポに新規 skeleton を作成 (Apache-2.0, Python 3.11).
159 実 GitHub repo init は user 承認後.
160 
161 構造:
162 
163 ```
164 lleval/
165 ├── pyproject.toml           # Apache-2.0, optional extras: ci/report/trace
166 ├── README.md
167 ├── LICENSE
168 ├── src/lleval/
169 │   ├── __init__.py          # public API
170 │   ├── config.py            # pydantic Config (5 model)
171 │   ├── runner.py            # ProgressiveMatrixRunner + Bench
172 │   ├── providers/
173 │   │   ├── __init__.py
174 │   │   └── promptfoo_yaml.py # 4 backend templates (openai/mamba/rwkv/...)
175 │   ├── analyzer/
176 │   │   └── honest_disclosure.py # 5+1 軸異常診断 skeleton
177 │   ├── report.py            # markdown + JSON
178 │   └── cli.py               # `lleval run config.yaml`
179 ├── examples/
180 │   ├── basic.yaml           # 1 provider × 1 size × 2 prompts
181 │   ├── progressive.yaml     # 1 provider × 5 sizes
182 │   └── multi_provider.yaml  # 4 provider (on-prem 3 + cloud 1) × 3 sizes
183 └── tests/unit/              # 20 件緑 (skeleton + providers + examples)
184 ```
185 
186 `promptfoo` を **fork ではなく wrap** する方針は portal 側の
187 `docs/spec/lleval_v0_1_implementation_notes.md` で確定. 実 promptfoo
188 subprocess 呼び出しは v0.1.0a1 以降.
189 
190 `multi_provider.yaml` の構造で **「on-prem 3 + cloud 1」を同一 run** で
191 扱う設計が表現できる:
192 
193 ```yaml
194 providers:
195   - { name: ollama-local, backend: openai, base_url: http://localhost:11434/v1 }
196   - { name: mamba-local,  backend: mamba,  base_url: http://localhost:8080/v1 }
197   - { name: rwkv-local,   backend: rwkv,   base_url: http://localhost:18888/v1 }
198   - { name: anthropic-cloud, backend: anthropic, model: claude-haiku-4-5 }
199 ```
200 
201 これが lleval の差別化軸 #1 (on-prem + cloud 統一 A/B run).

241 ## 9. 教訓 (前倒し marathon から 3 つ)
242 
243 ### 教訓 1: credential 不要レイヤを **先に全部書く** とマラソンが組める
244 
245 実 backend / 実 LLM API / 実ハードウェアに依存しない部分は agent が単独で
246 書けます. 今回の 7 件はすべてその範囲に収まりました.
247 
248 逆に言うと credential / 外部 binary が必要な作業は **operator (人間) が
249 着手するときに 2 日のクリティカルパス** になります. agent は事前に skeleton
250 を整えて待つのが正解.
251 
252 ### 教訓 2: mock baseline が無いと honest disclosure が崩れる
253 
254 MockBackend を 5 軸 fitness に組み込むことで:
255 
256 - 公開ベンチに mock 数値が混入しない (runtime_metadata = `"unknown"` で publish gate がブロック)
257 - agent が独自に進化ループ / bench harness / lleval skeleton を実走確認できる
258 - 実 backend 統合時に shape が確定済 = 1 step で繋がる
259 
260 mock がしっかりしていないと, 実 backend を繋ぐ時点で shape の話し合いに
261 なって時間を食う.
262 
263 ### 教訓 3: PR ドラフトを **マージ前に書く** とレビュー観点が明確になる
264 
265 `docs/pr_drafts/optimize_core_2026_05_20_changelog.md` を **マージ前** に
266 書くことで, 3 epic を 1 branch に詰めた reviewability の悪さが見える化されて,
267 **3 PR に分ける案を推奨** が自然に出てきました.
268 
269 「branch を切ったあとで PR ドラフトを書く」だけで, review 観点 + revert 単位
270 + 残作業 が同時に整理される. 個人 OSS では特に効くプラクティス.
