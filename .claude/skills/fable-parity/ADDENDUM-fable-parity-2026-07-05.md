## 追記：Opus をオーケストレーションで「上位モデル」級にできるか — 作ったものと測定結果

> 本編（歩行進化・LLM マージ・性格ダイヤル）とは別テーマですが、同じ「手元の計算資源で LLM に何をさせられるか」の一環として、実際に組んで測った記録を追記します。感想でなく、作った物・実験設定・数字を出します。

**背景**：上位モデル（Opus より 1 段上のティア）がもうすぐ使えなくなる。そこで「1 パスの深い推論」の代わりに **オーケストレーション**（分解 → 並列に多様な試行 → 敵対的検証 → 統合）を"消費"して、手元の Opus を上位モデル級に引き上げられるかを検証した。

### 作ったもの（実体のあるコンポーネント）

1. **足場ワークフロー `deep-reason`**（JS オーケストレーション）：タスクを分解し、`first-principles / work-backwards / edge-cases-first / constraint-satisfaction` の 4 つの切り口で並列に解かせ、各試行を別コンテキストで敵対的に検証し、検証済みの最強部品を統合する。
2. **別系列検証 `ext_verify.py`**：荷重ある主張 1 件を、非 Anthropic の OpenAI Codex（gpt-5.4）に "反証せよ" と投げ、`{"verdict":"survives|refuted","reason":...}` を返す。`codex exec -s read-only` に STDIN でプロンプトを渡し、認証失敗等は `ok:false`（=未検証）にして"通過"扱いにしない fail-closed 設計。これを 4 つの検証系（計画検証・研究検証など）に配線した。
3. **degenerate ガード**：統合が `{"answer":"test"}` のような空回答を出荷したのを検知して、`合成が異常に短ければ最良の検証済み試行に戻す`ガードを追加（決定的テスト 4/4）。
4. **測定パイプライン**：客観タスクは **キーを Python の総当りで計算**（著者の勘違い防止）。品質タスクは **独立 codex を blind 判定者**にし、位置バイアスを消す決定的シャッフルつきで匿名 A/B/C をランクさせる。上位モデルの出力 15 本を凍結（消えたら二度と採れないため）。

### やった測定（設定と数字）

- **客観推論**：総当りでキーを計算した難タスク 9 本 ×（opus 単発 / 上位モデル単発 / opus+足場）の 3 アームを回し、キーと照合。→ 難易度を上げて再度 9 本。
- **品質**：オープンな設計・仕様・分析タスク 5 本を 3 アームで生成し、匿名で codex にランクさせた。さらに 10 本を追試（上位モデルだけ凍結し、opus 単発を後付けして 2 者比較）。合計 15 本。
- **判定の頑健性**：同じ 5 本を 3 回シャッフルして judge を回し、勝者が安定か確認した。

### 結果

**軸① 客観推論 → 天井。** opus 単発が **9/9、再挑戦も 9/9（累計 18/18）**、上位モデルとの差はゼロ。ここでは足場は無力どころか **1 問で自爆**（統合が空の `"test"` を出荷。上記ガードで修正）。

```js
const synthesisDegenerate = synthesis && synthAnswer.length < 40 && maxAttemptLen >= 120; // →破棄して最良試行に戻す
```

**軸② 品質 → タスク依存。** 15 タスクの blind 判定で、**素の Opus 単発はほぼ一度も 1 位にならず、上位モデルに 10/15 で負けた**（＝単発品質の差は実在）。ただし **上位モデルは設計・仕様で勝ち分析・デバッグで最下位**、**足場は分析で勝ち設計で退行**（統合の接ぎ木が 1 パスの一貫性を壊す）。一律に届くわけではない。

**軸③ 検証の相関盲点 → ここが本命で、実際に効いた。** 同じモデルの自己検証は同じ盲点を共有する。検証だけ別系列に出したら、**Opus の検証者が「確認済み」とした前提を、Codex が具体根拠で覆した**。

### 実例（すべて実際の出力）

**ext_verify — 真は残り偽は具体根拠で落ちる：**
```json
{"verdict":"survives","reason":"17 has no positive divisors other than 1 and 17."}
{"verdict":"refuted","reason":"21 is divisible by 3 and 7, so it is not prime."}
{"verdict":"refuted","reason":"list.sort() sorts the list in place and returns None, so no new sorted list is returned."}
```

**別系列が Opus の「確認済み」を覆した：** FastAPI レート制限の計画検証で、前提「ライブラリ X は 429 応答を async callback で customize でき、slowapi 型の例外ハンドラ API は無い」を **Opus は "confirmed"**。Codex の反証（実文）：

> 「その最新版に `FastAPILimiter.init` API も、Retry-After callback 用の retry metadata も見つからない。主張は customization 機構を過大評価している」

→ 前提は "uncertain" に格下げされ、計画に「着手前に実ソースを読んで食い違いを解消せよ」という検証ステップが自動挿入された。Opus 一色なら誤りをそのまま出荷していた。

**判定者 Codex の実講評（足場が勝った理由）：**
> q4（間欠 stale read）：「1e-4 という率から過剰推論せず、replica 遅延とキャッシュ汚染を source tagging と primary-only カナリアで切り分けている」

### 持ち帰り（実務の地図）

| 状況 | 使うもの | 理由（実測ベース） |
|---|---|---|
| 客観的に正解が決まる推論 | **何も足すな** | 天井。足場は自爆リスクすらある |
| 微妙な技術点を詰める分析・デバッグ | **足場（並列試行＋検証）** | 検証が生成より安く、実測で勝てる |
| 広く一貫した設計・仕様 | **素の 1 パス** | 統合の接ぎ木が一貫性を壊す |
| 前提の誤りが高コストな計画・移行 | **別系列で検証** | Opus の「確認済み」を実際に覆した |

### 正直な但し書き

数値は小 N・単一 blind 判定の指標値。judge を 3 回回すと **5 タスク中 2 つしか勝者が安定せず**、測定自体が思ったより noisy だった（ただし「素 Opus はほぼ一度も best にならない・1/15」は固い）。**「一律 parity 達成」という美味しい主張は、正直に測ったら成立しなかった。** 作ったのは、勝った気になる材料ではなく、**別系列検証という効く道具**と、**いつ足場を使う/使わないかの地図**でした。
