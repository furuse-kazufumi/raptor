## 追記：オーケストレーションで Opus を「上位モデル」級にできるか、正直に測ってみた

> 本編（歩行進化・LLM マージ・性格ダイヤル）とは別テーマですが、同じ「手元の計算資源で LLM に何をさせられるか」の一環として、もう一本の実験記録を追記します。コード・実出力・失敗例まで出します。

上位モデル（Opus より 1 段上のティア）がもうすぐ使えなくなる。だから「並列に何度も考えさせて敵対的に検証する足場（オーケストレーション）」で、手元の Opus をそのモデル級に引き上げられないか——を実装して、**独立の判定者で盛らずに測った**。結論から：**一律には届かない。でも明日から使える道具と運用地図は残った。**

### 何が嬉しいのか（メリット）

- **弱い/安いモデルの信頼性を「計算」で買える。** 1 パスの当たり外れに賭ける代わりに、分解→並列試行→敵対的検証→統合を消費して外れを削る。新しい知識は生まないが、信頼性は買える。
- **「自分の宿題を自分で採点する」問題を潰せる（本命）。** 同じ重みのモデルは同じ盲点を共有する。検証だけ別系列に出すと、同族なら見逃す誤りを突ける。
- **モデル比較を正直にやるレシピが手に入る。** キーは総当りで計算／判定は独立系列に blind で／位置バイアスはシャッフルで消す。
- **トークンを無駄に燃やさない地図が手に入る。** どのタスクで足場が効き、どこで逆効果かが分かる。

### 3 つの軸で結論が正反対になった

**① 客観的に正解が決まる推論**（総当りでキーを計算したパズル・数え上げ・状態機械）:
**Opus は既に天井**。上位モデルとの差はゼロ（難易度を上げて 2 度測り 18/18）。
足場は無力どころか、1 問で統合エージェントが `{"answer":"test","confidence":"high"}` という**中身が空の合成を出荷して自爆**した——素の Opus が解ける問題に"失敗する余地"を足していた。修正は隠さず、統合結果が異常に短ければ検証済みの最良試行に戻すガードを入れた（決定的テスト 4/4）：

```js
// 実 attempt(≥120字)があるのに合成 answer が<40字なら degenerate として破棄→best-verified attempt に fallback
const synthesisDegenerate = synthesis && synthAnswer.length < 40 && maxAttemptLen >= 120;
```

**② オープンな品質**（設計・仕様・分析。正解キーが無いので非 Anthropic の Codex に匿名 blind ランク）:
初めて構造が出た。**素の Opus 単発は 15 タスク中ほぼ一度も 1 位にならない**（差は実在）。ただし**上位モデルは設計・仕様で強く分析・デバッグで最下位、足場は分析で勝ち設計で退行**する。統合の接ぎ木が、1 パスの一貫した設計の良さを壊すためだ。**足場はタダでなく、一様に良くもない。タスク依存。**

**③ 検証の相関盲点（本命）**: 同じモデルの自己検証は同じ盲点を共有する。検証だけ別系列（OpenAI Codex/gpt-5.4）に出した。

### どう実装したか（要点）

足場の本体は 4 手：**分解 → N 個の別々の切り口で並列試行 → clean な別コンテキストで「壊せ」と敵対的検証 → 最強の検証済み部品を統合**。独立性が命（同じ文脈を共有した批評家は同じ盲点を継ぐ）。

別系列検証は最小の道具にした。**codex を "反証専門" で呼び、クリーンな 1 行 JSON verdict を返す**だけ：

```python
# codex は複数行 prompt を STDIN で読む（positional だと空プロンプトに誤読）。Windows は codex.CMD → shutil.which でフルパス解決
p = subprocess.run([shutil.which("codex"),"exec","-s","read-only"], input=prompt, capture_output=True, text=True)
# プロンプトは refute-by-default（不確実なら反証扱い）。認証切れ等の失敗は ok:false=unverified にして "通過" 扱いにしない（fail-closed）
```

### 実例（すべて実際の出力）

**ext_verify — 真は残り、偽は具体根拠で落ちる:**

```json
{"verdict":"survives","reason":"17 has no positive divisors other than 1 and 17."}
{"verdict":"refuted","reason":"21 is divisible by 3 and 7, so it is not prime."}
{"verdict":"refuted","reason":"list.sort() sorts the list in place and returns None, so no new sorted list is returned."}
```

**別系列が Opus の「確認済み」を覆した（本命の実証）:** FastAPI レート制限計画で、ある前提を——

> 「ライブラリ X は 429 応答を async callback で customize でき、slowapi 型の例外ハンドラ API は無い」

**Opus の検証者は "confirmed"** とした。ところが **Codex が反証**（実際の理由文）：

> 「その最新版に `FastAPILimiter.init` API も、Retry-After callback 用の retry metadata も見つからない。主張は customization 機構を過大評価している」

結果、前提は "uncertain" に格下げされ、計画に「着手前に実ソースを読んで Opus と Codex の食い違いを解消せよ」という検証ステップが自動で入った。**Opus 一色なら自信のある誤りをそのまま出荷していた。**

**判定者（Codex）の実講評**（分析系で足場が勝った理由の抜粋）:

> q4（間欠 stale read の根本原因）：「1e-4 という率から過剰推論せず、replica 遅延とキャッシュ汚染を source tagging と primary-only カナリアで切り分けている」
> q5（ホットカウンタ）：「"Redis を前に置いても coalescing か durable log を足さない限り Redis 障害時の耐久書き込み上限は上がらない"という核心の機微を取れている」

### 持ち帰り（実務の地図）

| 状況 | 使うもの | 理由 |
|---|---|---|
| 客観的に正解が決まる推論 | **何も足すな** | 天井。足場は自爆リスクすらある |
| 微妙な技術点を詰める分析・デバッグ | **足場（並列試行＋検証）** | 検証が生成より安く、実測で勝てる |
| 広く一貫した設計・仕様 | **素の 1 パス** | 統合の接ぎ木が一貫性を壊す |
| 前提の誤りが高コストな計画・移行・調査 | **別系列で検証** | Opus の「確認済み」を実際に覆した |

### 正直な但し書き

数値は小 N・単一 blind 判定の指標値。judge を 3 回シャッフルで回すと **5 タスク中 2 つしか勝者が安定しなかった**（測定自体が思ったより noisy）。ただし集計（足場 3 / 上位 2 / 素 Opus 0）は多数決で再現し、**素の Opus は 15 判定中ほぼ一度も best にならない（1/15）**——ここは固い。**「一律 parity 達成」という美味しい主張は、正直に測ったら成立しなかった。** 研究の価値は勝った気になることでなく、内訳を正直に開示すること——という回でした。
