## Task

Explain Kahan (compensated) summation. First show exactly why naive left-to-right floating-point summation loses precision (the mechanism: adding a small number to a large running sum drops low-order bits at rounding). Then show what Kahan's running compensation term recovers and how (walk the algorithm's update). Finally state its LIMITS precisely: what error bound Kahan achieves vs naive (O(1) vs O(n) growth in units of epsilon), and what it does NOT fix (e.g. catastrophic cancellation from subtracting nearly-equal numbers, or ill-conditioned sums).

## Fable answer

# Kahan (Compensated) Summation

## 0. Floating-point model (needed for everything below)

IEEE-754 arithmetic guarantees that each single operation is correctly rounded:

```
fl(a ⊕ b) = (a + b)(1 + δ),   |δ| ≤ u
```

where `u` is the unit roundoff (`u = 2⁻⁵³ ≈ 1.1e-16` for binary64). Each addition is *individually* almost perfect; the problem is purely about how per-operation errors **accumulate** across n additions.

## 1. Why naive left-to-right summation loses precision

```
s = 0
for x in xs: s = s + x
```

**Mechanism — bit alignment and truncation.** A binary64 significand holds 53 bits. To compute `s + x`, the hardware aligns the binary points: `x`'s significand is shifted right by `log2(|s|/|x|)` bit positions. Every bit of `x` that falls below `ulp(s)` (the value of `s`'s last significand bit) cannot be represented in the 53-bit result and is rounded away.

```
s = 1e16    ≈ 1.0001110000110...  × 2^53      ulp(s) = 2
x = 1.0     =                                1.0
                                              ^ entirely below ulp(s)
fl(s + x) = 1e16   (x vanished completely; round-to-even drops it)
```

Concretely, in binary64: `1e16 + 1.0 == 1e16` exactly. Sum `1.0` ten million times onto `1e16` naively and you still get `1e16` — an absolute error of `1e7` — even though each individual addition was "correctly rounded."

**How the error grows.** The standard forward bound for recursive summation is

```
|Ŝ − S| ≤ (n − 1) · u · Σ|xᵢ|  + O(u²)
```

Each partial sum contributes up to one rounding of magnitude `u·|partial sum|`, and there are n−1 of them: worst-case error grows **linearly in n** (in units of ε). With random signs of the rounding errors, expected growth is O(√n)·u — better, but still unbounded in n. The damage is worst when the running sum is large while the addends are small (the "swamping" case above), because then *every* addend loses its low-order bits, and those losses are systematically in the same direction if the data is.

## 2. What Kahan recovers, and how

```
s = 0.0
c = 0.0                    # running compensation: the low-order bits lost so far
for x in xs:
    y = x - c              # (1) pre-correct the input by what was lost previously
    t = s + y              # (2) the big add; low-order bits of y are lost here
    c = (t - s) - y        # (3) recover EXACTLY what was lost, with sign flipped
    s = t
```

**Why step (3) works.** Algebraically `(t − s) − y ≡ 0`; in floating point it is not, and that non-zero residue *is* the rounding error. The key fact (Dekker/Fast2Sum): if `|s| ≥ |y|`, then

- `t = fl(s + y)` loses information, **but**
- `fl(t − s)` is computed **exactly** (no rounding): `t` and `s` are close in magnitude, so the subtraction is representable (Sterbenz-adjacent argument). `t − s` equals *the part of y that actually made it into the sum*.
- `fl((t − s) − y)` is then also exact, and equals `(part of y added) − (all of y)` = **−(the part of y that was dropped)**.

So `c` holds, with a sign flip, precisely the low-order bits that were shifted off the end in step (2). Step (1) of the *next* iteration re-injects them: `y = x − c` adds the lost tail back onto the next addend, where it lives among small numbers of comparable magnitude and is not truncated. The error never accumulates in `s`; it is parked in `c` and recycled every iteration.

**Worked example** (binary64, `s = 1e16`, adding `x = 1.0` repeatedly; `ulp(1e16) = 2`):

| step | y = x − c | t = s + y | c = (t − s) − y | s |
|---|---|---|---|---|
| 1 | 1 − 0 = 1 | fl(1e16+1) = 1e16 | (1e16−1e16) − 1 = **−1** | 1e16 |
| 2 | 1 − (−1) = 2 | fl(1e16+2) = 1e16+2 (exact, = ulp) | (2) − 2 = 0 | 1e16+2 |
| 3 | 1 − 0 = 1 | 1e16+2 | −1 | 1e16+2 |
| … | | | | |

Naive summation loses every single `1.0` forever. Kahan banks each lost unit in `c` until two units reach `ulp(s)`, then deposits them — nothing is lost. The final answer is off by at most ~1 ulp regardless of how many terms you add.

## 3. Error bounds: O(1) vs O(n)

| method | forward error bound | relative error vs Σ\|xᵢ\| |
|---|---|---|
| naive recursive | `(n−1)·u·Σ|xᵢ| + O(u²)` | **O(n·u)** |
| pairwise/tree | `O(log n)·u·Σ|xᵢ|` | O(u·log n) |
| Kahan | `(2u + O(n·u²))·Σ|xᵢ|` | **O(u)** — constant in n |

Kahan's bound (Knuth TAOCP vol. 2; Goldberg 1991): the error is at most `2u·Σ|xᵢ|` up to the `O(nu²)` tail — i.e. essentially **two rounding errors total, independent of n**, until n approaches `1/u ≈ 9e15` and the second-order term matters. That is the whole payoff: error growth in units of ε goes from linear-in-n to constant.

## 4. Limits — what Kahan does NOT fix

**(a) The bound is relative to Σ|xᵢ|, not to |S|.** This is the crucial fine print. Define the condition number of the sum κ = Σ|xᵢ| / |Σxᵢ|. Kahan's *relative error with respect to the true sum* is ~`2u·κ`. If the sum is **ill-conditioned** — large positive and negative terms cancelling to a tiny result (κ ≫ 1) — Kahan's answer can still be relatively garbage. Example: terms of magnitude ~1e16 cancelling to a true sum of ~1: κ ≈ 1e16, and `2u·κ ≈ 2` — potentially 200% relative error. Kahan removes *accumulation* error; it cannot manufacture the bits of information that cancellation destroys. (Correctly rounded results for ill-conditioned sums need exact/long-accumulator methods: Shewchuk expansions, Demmel–Hida, Neumaier's `xsum`, double-double cascades.)

**(b) Catastrophic cancellation of *inputs* is upstream of summation.** If `x₁ = fl(a)` and `x₂ = fl(−b)` with a ≈ b, the inputs already carry relative errors ~u from their own computation; `x₁ + x₂` amplifies those inherited errors by κ. No summation algorithm — Kahan, pairwise, or even *exact* summation — can fix this, because the exact sum of the *rounded inputs* is already wrong. Compensation addresses errors *created by the summation*, nothing else.

**(c) The Fast2Sum precondition can fail: |y| > |s|.** Kahan omits the magnitude test, so when an addend exceeds the running sum, `c` captures only an approximation of the error (the guaranteed bound survives, but exactness doesn't). Classic pathological case:

```
[1.0, 1e100, 1.0, -1e100]   → true sum = 2.0
Kahan gives 0.0
```

Step-by-step: adding `1e100` swamps `s=1`; `c` correctly records `−1`... but then `y = 1 − (−1) = 2` vanishes against `1e100` and its loss is re-recorded; finally adding `−1e100` produces `t = 0` and `c = (0 − 1e100) − (−1e100 + ...)` — the compensation itself gets truncated when the sum's magnitude collapses. **Neumaier's variant (Kahan–Babuška)** fixes this by branching on `|s| ≥ |x|` to decide which operand's low bits to salvage, and returns exactly `2.0` here — at the same O(u) bound and near-same cost. If input magnitudes vary wildly with sign changes, prefer Neumaier.

**(d) The compiler can delete the algorithm.** `c = (t − s) − y` is algebraically zero; under `-ffast-math`, `-Ofast`, ICC's default fp-model, or any reassociation-licensed optimization, the compensation folds to `c = 0` and you silently get naive summation back. You must compile the summation kernel with strict FP semantics (`-fno-fast-math`, `volatile` tricks, or `#pragma float_control(precise)`). Similarly, x87 80-bit intermediates or an FMA-contracted rewrite can perturb the exact-cancellation reasoning (double rounding), though on SSE/AVX binary64 this is a non-issue.

**(e) It is not a correctly-rounded sum.** ~2u relative-to-Σ|xᵢ| ≠ 0.5 ulp of the true sum. If you need reproducible/bitwise-deterministic or correctly rounded results (parallel reductions, cross-platform), use exact accumulators (xsum, ReproBLAS), not Kahan.

**(f) Cost and alternatives.** 4 adds per element vs 1 (~2–4× slower scalar; it also serializes the loop-carried dependency, hurting vectorization — mitigate by running k independent Kahan lanes and merging). For most well-conditioned workloads, **pairwise summation** (O(u log n), what NumPy's `sum` uses) is nearly as accurate and SIMD-friendly; Kahan earns its cost when n is huge, the data is adversarial, or you need the n-independent bound.

**Summary in one line.** Kahan turns per-step truncation loss (small addend's low bits sliding off the end of a large accumulator) into a recoverable quantity via the exact-error identity `c = ((s+y) − s) − y`, cutting error growth from O(n·u) to O(u) relative to Σ|xᵢ| — but it is powerless against ill-conditioning (κ = Σ|xᵢ|/|S|), inherited input error, sign-alternating magnitude swings (use Neumaier), and reassociating compilers.
