# q13 — fable-raw (archetype: distributed)

## Task

Explain precisely why two-phase commit (2PC) BLOCKS on coordinator failure: give the exact scenario (which participant states, what they cannot decide, and why) where a participant is stuck indefinitely. Then explain how three-phase commit (3PC) removes the blocking under a synchronous model, the extra cost it pays, and the failure model (network partition / asynchrony) under which 3PC still fails — and how a consensus-based commit (Paxos/Raft-backed) addresses it. Be precise about the assumptions each protocol needs.

## Fable answer

## 1. Why 2PC blocks: the exact scenario

**Protocol recap and the critical state.** In 2PC a participant that receives `PREPARE` and votes **YES** must first force-write a *prepared* log record and hold all its locks. From that instant until it receives the decision, it is in the **uncertain (prepared) window**:

- It **cannot unilaterally abort** — it has surrendered its veto; the coordinator may already have collected all-YES, force-logged `COMMIT`, and the global decision may be commit.
- It **cannot unilaterally commit** — some other participant may have voted NO, or the coordinator may have timed out and decided abort.

**The blocking scenario, precisely:**

1. Participants P1…Pn all vote YES (all are in *prepared*).
2. The coordinator collects the votes, decides (say, commit), force-logs the decision, sends `COMMIT` to **P1 only**, then **crashes**. Simultaneously (or shortly after) **P1 crashes** — possibly after applying the commit and releasing its locks, with effects now externally visible.
3. P2…Pn time out and run the *cooperative termination protocol*: they query each other. Every reachable peer is also in *prepared*. The only nodes that knew the decision — the coordinator and P1 — are down.

P2…Pn are now stuck: the true outcome could be **commit** (coordinator logged COMMIT, P1 committed) *or* **abort** (coordinator's log says abort, P1 never acted) and both are consistent with everything the survivors can observe. Choosing either unilaterally risks contradicting an already-executed decision at P1 → atomicity violation. So they must **block, holding locks, until the coordinator (or P1) recovers** — potentially forever if the machine is gone. Note this holds *even with a synchronous network and perfect failure detection*: the problem is not "can't tell if it's dead," it's that the decision knowledge itself is trapped in the dead nodes.

**Why this is structural (Skeen's condition).** A commit protocol is non-blocking iff no reachable local state is simultaneously "adjacent" to both a global-commit and a global-abort outcome, i.e., there must be no state in which an operational site is uncertain while some (possibly crashed) site may already have committed. In 2PC, the *prepared* state is directly adjacent to both `COMMITTED` and `ABORTED` — a participant can be uncertain while another has already committed. That adjacency **is** the blocking; no timeout policy can fix it.

## 2. How 3PC removes blocking (synchronous model)

**The fix: break the adjacency.** 3PC (Skeen, 1981) inserts a buffer state between "voted YES" and "committed":

1. **canCommit** — votes collected (same as 2PC phase 1).
2. **preCommit** — on all-YES, coordinator sends `PRE-COMMIT`; participants move to state *PC* and ACK. Key invariant established: **no participant commits until every participant has left the uncertain state** (everyone is at least in *PC*).
3. **doCommit** — only after all ACKs does the coordinator send `COMMIT`.

**Why survivors can now always decide.** On coordinator failure, survivors elect a new coordinator and pool their states:

- Any survivor in `COMMITTED` → commit everywhere (safe: implies all had reached PC).
- Any survivor in `ABORTED` / voted NO → abort everywhere.
- Some survivor in *PC*, none aborted → decision was necessarily heading to commit (coordinator only sends PRE-COMMIT on all-YES) → re-issue PRE-COMMIT, then commit.
- **All survivors still uncertain (voted YES, no PRE-COMMIT seen)** → the invariant guarantees **no one anywhere — including crashed nodes — can have committed** (committing requires everyone in PC, but *these* nodes aren't). → **abort is provably safe.** This is exactly the case that blocked 2PC.

The uncertain state is no longer adjacent to `COMMITTED`; Skeen's non-blocking condition is satisfied.

**Assumptions 3PC needs (all load-bearing):**
- **Synchronous system**: known bounds on message delay and processing time, so a timeout is a *perfect* failure detector (timeout ⇒ genuinely crashed, never merely slow).
- **Crash-stop, no network partitions**: unreachable = dead; crashed nodes don't rejoin mid-termination-protocol (recovery must go through a separate protocol).
- Reliable channels among survivors; non-Byzantine faults.

**Extra cost:** one additional round trip (3 phases vs 2 → commit latency ~1.5×), an extra broadcast + ACK set (~5n vs ~3n messages), an extra forced log write per participant (the PC record), plus the complexity of election + termination protocol. Locks are held longer on every transaction to buy availability in the rare failure case — one reason real systems mostly didn't adopt it.

## 3. Where 3PC fails: partitions and asynchrony

The synchrony assumption is exactly what real networks violate, and 3PC's safety (not just liveness) depends on it.

**Split-brain scenario:**
1. All vote YES. Coordinator sends `PRE-COMMIT`, which reaches P1, P2, then the network **partitions**: {P1, P2} | {P3, P4, coordinator crashed or on either side}.
2. Each side's timeout fires; each side treats the other as *crashed* (a timeout cannot distinguish crashed from partitioned/slow) and runs the termination protocol independently.
3. Side A ({P1, P2}, in *PC*): rule "someone in PC → **commit**." They commit.
4. Side B ({P3, P4}, still uncertain): rule "all uncertain → **abort** is safe." They abort.
5. Partition heals: P1/P2 committed, P3/P4 aborted — **atomicity violated**. Same failure mode arises from asynchrony alone (a paused/slow node falsely declared dead that later acts on stale state), and from certain crash-recovery interleavings.

The deep reason is **FLP**: atomic commit's decision step embeds consensus, and no deterministic protocol in an asynchronous system with even one crash can guarantee both safety and termination. 3PC resolves 2PC's blocking by *spending safety under partition/asynchrony to buy liveness*. (Quorum-based variants like E3PC restore partition-safety, but only by adding majority machinery — i.e., by becoming consensus.)

## 4. Consensus-based commit (Paxos/Raft-backed)

**Idea:** the single point whose amnesia causes 2PC blocking — the coordinator's knowledge of the decision — is replaced by a **replicated, majority-quorum decision**. Two standard constructions:

- **Paxos Commit (Gray & Lamport 2006):** each participant's vote (Prepared/Aborted) is the value of its own Paxos instance across 2F+1 acceptors; the transaction commits iff every instance chooses *Prepared*. Instructive degenerate case: with F=0 (one acceptor), Paxos Commit *is* 2PC — 2PC is the F=0 point of the family, which is precisely why it blocks on one failure.
- **Replicated coordinator (Spanner-style):** run 2PC, but the coordinator (and each participant group) is a Raft/Multi-Paxos state machine. The commit/abort decision is committed to the coordinator group's replicated log **before** being announced.

**Why this fixes the blocking scenario of §1:** when the coordinator leader dies, the decision is not lost — it is durable on a majority of its replica group. A new leader is elected by any majority, reads the log (or, if no decision was logged, safely logs *abort* — quorum intersection guarantees it cannot conflict with a decided commit), and drives the protocol to completion. The "knowledge trapped in a dead node" state cannot occur.

**What it guarantees, precisely:**
- **Safety unconditionally** — under full asynchrony, partitions, arbitrary message loss/reordering/duplication (crash faults, non-Byzantine): quorum intersection makes two contradictory decisions impossible. This is what 3PC lacks.
- **Liveness conditionally** — FLP is not beaten, it is *relocated*: progress requires a majority of each replica group up and mutually connected, plus eventual partial synchrony (for stable leader election). A **minority partition still blocks** (participants there hold locks and wait) — but it blocks *consistently*, and any majority side makes progress. Availability of decisions is thus F-fault-tolerant with 2F+1 replicas, vs F=0 for 2PC.

**Assumptions:** 2F+1 replicas per consensus group; crash(-recovery) faults with stable storage; fair-lossy channels; partial synchrony for liveness only, never for safety.

## 5. Summary table

| | 2PC | 3PC | Paxos/Raft-backed commit |
|---|---|---|---|
| Blocks on coordinator failure | Yes (prepared participants, if decision-holders all down) | No (given its model) | No, if a majority of the coordinator group is reachable |
| Safety model | Any asynchrony/partition (safe, just blocks) | **Requires synchrony + no partitions**; violated ⇒ split-brain inconsistency | Any asynchrony/partition |
| Liveness model | Requires coordinator recovery | Synchronous, crash-stop | Majority up + partial synchrony |
| Failure-detection need | None for safety | **Perfect** (timeout ⇒ crashed) | Unreliable OK (eventually-accurate for liveness) |
| Cost | 2 rounds, ~3n msgs, 2 forced writes/participant path | 3 rounds, ~5n msgs, extra forced write, election protocol | Consensus round(s) per decision, 2F+1 replicas per group, leader machinery |
| Fault tolerance of the decision | F=0 | Any minority of crashes, zero partitions | F crashes per group of 2F+1, partitions tolerated |

One-line essence: 2PC blocks because the decision lives in one place and a YES-voter has surrendered its veto; 3PC un-blocks by ensuring "someone committed ⇒ everyone knew," but that inference is only sound when timeouts are truthful; consensus-based commit makes the decision itself a majority-replicated fact, keeping atomicity unconditional and confining unavoidable (FLP) blocking to minority partitions.
