# q12 — fable-raw (archetype: concurrency)

## Task

Design a bounded blocking queue (fixed capacity) for multiple producers and multiple consumers using ONLY a mutex and condition variable(s). Specify the exact lock/wait/signal discipline (which predicate each wait re-checks, why it MUST be a while-loop not an if, when to signal vs broadcast). Explain the two classic bugs — lost wakeup and the thundering-herd / spurious-wakeup problem — and show precisely how your discipline prevents each. State whether one condvar or two is correct and why.

## Fable answer

# Bounded Blocking Queue: Mutex + Condition Variables — Complete Design

## 1. State and invariants

```c
typedef struct {
    item_t     *buf;        // ring buffer, length = capacity
    size_t      capacity;   // fixed, > 0
    size_t      count;      // # items currently stored; INVARIANT: 0 <= count <= capacity
    size_t      head;       // next slot to dequeue from
    size_t      tail;       // next slot to enqueue into
    pthread_mutex_t m;      // guards ALL fields above
    pthread_cond_t  not_full;   // predicate: count < capacity
    pthread_cond_t  not_empty;  // predicate: count > 0
} bq_t;
```

**Ground rules of the discipline:**

- Every read or write of `count/head/tail/buf` happens while holding `m`. No exceptions — not even "harmless" reads like a `size()` peek used for a decision, because any decision based on unlocked state is stale the instant it's made.
- Each condition variable is permanently associated with exactly one *predicate over the shared state*:
  - `not_full` ⇔ `count < capacity` (what producers wait for)
  - `not_empty` ⇔ `count > 0` (what consumers wait for)
- A thread may call `pthread_cond_wait(cv, &m)` only while holding `m`, and only after testing the predicate under `m` and finding it false.
- Any thread that *makes a predicate true* (falsifies the wait condition) signals the corresponding condvar **while still holding the mutex** (or immediately after unlocking — both are correct; see §6).

## 2. The operations

```c
void bq_put(bq_t *q, item_t x) {
    pthread_mutex_lock(&q->m);
    while (q->count == q->capacity)            // MUST be while, not if
        pthread_cond_wait(&q->not_full, &q->m); // atomically: unlock m + sleep; relock m on return
    // Here: m held AND count < capacity — predicate guaranteed by the loop, nothing else
    q->buf[q->tail] = x;
    q->tail = (q->tail + 1) % q->capacity;
    q->count++;
    pthread_cond_signal(&q->not_empty);         // we made "count > 0" true (or truer)
    pthread_mutex_unlock(&q->m);
}

item_t bq_get(bq_t *q) {
    pthread_mutex_lock(&q->m);
    while (q->count == 0)                       // MUST be while, not if
        pthread_cond_wait(&q->not_empty, &q->m);
    item_t x = q->buf[q->head];
    q->head = (q->head + 1) % q->capacity;
    q->count--;
    pthread_cond_signal(&q->not_full);          // we made "count < capacity" true
    pthread_mutex_unlock(&q->m);
    return x;
}
```

**Which predicate each wait re-checks:**

| Waiter | Waits on | Re-checked predicate (under `m`, every wakeup) |
|---|---|---|
| producer in `put` | `not_full` | `count < capacity` — i.e., loop `while (count == capacity)` |
| consumer in `get` | `not_empty` | `count > 0` — i.e., loop `while (count == 0)` |

**Who signals what:** `put` signals `not_empty` after every successful insert; `get` signals `not_full` after every successful remove. Signal exactly one waiter per state change, because one insert creates capacity for exactly one `get` to proceed, and one remove creates room for exactly one `put`. (Broadcast cases: §5.)

## 3. Why `while`, never `if` — four independent reasons

The only thing `pthread_cond_wait` guarantees on return is: *the mutex is re-held*. It guarantees **nothing** about the predicate. Between the moment a signaler makes the predicate true and the moment the woken thread reacquires the mutex, the world can change. Concretely:

1. **Mesa (signal-and-continue) semantics.** POSIX/C++/Java condvars are Mesa-style: `signal` only moves a waiter to "runnable"; it does not hand over the mutex or the CPU. The signaled thread must *re-compete* for the mutex. This is the root cause of reasons 2–3.

2. **Stolen wakeups (the killer with multiple consumers).** Consumer C1 waits on `not_empty`. Producer P inserts one item, signals, unlocks. Before C1 reacquires `m`, consumer C2 — which was *never waiting*, it just arrived at `bq_get` — grabs the mutex, sees `count == 1`, takes the item, leaves. C1 finally acquires `m` with `count == 0`. With `if`, C1 would now execute the dequeue on an **empty** buffer: it reads garbage from `buf[head]` and drives `count` to `(size_t)-1`, permanently corrupting the queue (both predicates now look "true" to everyone; capacity checks are bypassed forever). With `while`, C1 re-tests `count == 0`, finds it true, and goes back to sleep. Correct.

3. **Spurious wakeups.** POSIX explicitly permits `pthread_cond_wait` to return with *no* signal at all (an artifact of efficient futex/multiprocessor implementations, and of signal-handler interactions). C++ `std::condition_variable` and Java `Object.wait` document the same. With `if`, a spurious wakeup proceeds straight into the critical section with a false predicate — same corruption as above. With `while`, it costs one extra predicate test and a re-sleep.

4. **Broadcast overshoot.** If you ever use `broadcast` (or a single condvar shared by both roles — §7), one state change wakes N waiters but enables only k ≤ N of them. The N−k losers must re-check and re-sleep. `if` gives all N a green light.

So the loop is not defensive paranoia; it is the *definition* of correct condvar use: **the predicate, tested under the mutex, is the truth; the wakeup is merely a hint that the predicate might now be true.** A useful mental model: `wait` in a loop is logically equivalent to a polling loop `while (!P) { unlock; relock; }` — the condvar only makes the busy-wait cheap. Anything that would be wrong for the polling loop (acting on `!P`) is wrong here too.

## 4. Bug #1: Lost wakeup — and exactly how the discipline prevents it

**The bug.** A lost wakeup occurs when the waiter's *test* of the predicate and its *going to sleep* are not atomic with respect to the signaler's *update* + *signal*:

```
Consumer (BUGGY: tests without mutex, or unlocks before waiting)
    T1: sees count == 0
                                   Producer
                                   T2: lock; count=1; signal(not_empty); unlock
    T3: blocks on not_empty        // signal at T2 hit zero waiters — it is NOT queued
    ... sleeps forever (if no further put ever comes)
```

Condvar signals are **not sticky** (unlike semaphore posts): a signal with no waiter present is a no-op. So a signal that fires in the window between "I decided to sleep" and "I am actually asleep" evaporates.

**How the discipline prevents it — the atomicity argument, precisely:**

1. The waiter tests `count == 0` **while holding `m`**.
2. `pthread_cond_wait(&not_empty, &m)` **atomically** releases `m` and enqueues the caller on the condvar. "Atomically" here has a precise POSIX meaning: no other thread can acquire `m`, change the state, and signal the condvar *in between* the release and the enqueue such that the signal misses this waiter.
3. The signaler can only change `count` while holding `m`. Therefore the producer's `count++` + `signal` happens either **(a) before** the waiter's test — then the waiter sees `count > 0` and never sleeps; no wakeup needed — or **(b) after** the waiter is already registered on the condvar — then the signal finds the waiter and wakes it.

There is no third interleaving. The mutex serializes the predicate change against the test, and the atomic release-and-wait closes the test→sleep window. Both halves are required: testing under the mutex but calling a hypothetical `unlock(); cond_sleep();` pair would reopen the window; an atomic wait without testing under the mutex would too.

Corollary rule: **never touch the predicate state or decide to wait without holding `m`, and never signal a predicate change you made without holding `m`** (for the signal itself, see §6 — the *state change* must be under the lock; the signal call may trail it).

## 5. Bug #2: Thundering herd / spurious-wakeup problem — and how the discipline contains it

Two related phenomena, one waste-shaped, one correctness-shaped:

**(a) Spurious/stolen wakeups as a correctness problem** — fully covered by the `while` loop (§3). A woken thread whose predicate is false does no harm: it re-sleeps. This is the *safety* half.

**(b) Thundering herd as a performance/liveness problem.** If every state change did `broadcast`, then one `put` into an empty queue wakes *all* W waiting consumers; all W pile onto the mutex; one wins the item; W−1 reacquire the mutex serially just to discover `count == 0` and sleep again. Cost: O(W) context switches and mutex convoy per item — the herd. Worse, on a single condvar (§7) a broadcast wakes threads of the *wrong role* too.

**Containment by discipline:**

1. **Signal, don't broadcast, when one state change enables at most one waiter.** In this queue, `put` adds exactly one item ⇒ at most one blocked consumer can make progress ⇒ `pthread_cond_signal(&not_empty)`. Symmetrically for `get`/`not_full`. Exactly one thread is disturbed per event.
2. **Dedicated condvar per predicate** ⇒ a signal can never land on a thread of the wrong role (a producer will never consume a "data available" wakeup). This is what makes `signal` *safe*, not merely efficient — see §7 for why this matters critically.
3. **`while` loop as the backstop** ⇒ on the occasions the kernel does wake extra threads anyway (spurious wakeups; some implementations may wake more than one on `signal` — POSIX permits waking "at least one"), the extras harmlessly re-sleep. So the discipline is: *use `signal` for throughput, but write code that would remain correct under `broadcast`*. Correctness never depends on "exactly one woke up".

**When `broadcast` is actually required** (the honest edge cases — using `signal` here is a real bug, a form of lost wakeup by misdirection):

- **Shutdown/close:** `bq_close()` must wake *every* waiter on *both* condvars so all can observe `closed` and return (each wait loop becomes `while (count == 0 && !q->closed)`, and after the loop: `if (count == 0 && closed) return QUEUE_CLOSED;` — drain-then-fail, still fail-closed once drained).
- **A single state change that may enable multiple waiters:** e.g., a bulk `put_n(k items)` or `resize(capacity)`. Either `broadcast`, or issue k `signal`s.
- **One shared condvar for both roles** (§7): then every wakeup-worthy event must `broadcast`, because `signal` might pick a waiter whose predicate is still false, who re-sleeps, and the *one* wakeup the event was entitled to has been absorbed by the wrong party — deadlock with work available. That is the subtle trap: **`signal` is only safe when every thread waiting on that condvar is waiting for the same predicate** (or when any waiter can serve the event).

## 6. Signal while holding the lock, or after releasing it?

Both are **correct**; the discipline only mandates that the *state mutation* happens under `m`.

- **Signal-with-lock-held** (as written above): simpler to reason about (state change and notification are one atomic package from any observer's viewpoint); required anyway when the waiter might destroy the condvar right after being woken (e.g., queue teardown handshake). Theoretical downside: the woken thread may immediately block on the still-held mutex ("hurry up and wait"); modern implementations (glibc wait-morphing, futex requeue) largely erase this cost.
- **Unlock-then-signal**: avoids that bounce; still correct **only because** the woken thread re-checks the predicate under `m` — between your unlock and your signal, a third thread may have consumed the state change, and the `while` loop absorbs that. Caveat: it can cost strict FIFO fairness (a barger can slip in), which this queue does not promise anyway.

If unsure, hold the lock while signaling; it is never wrong, merely (marginally, and usually not measurably) slower.

## 7. One condvar or two?

**Two is the correct design. One condvar can be made correct, but only by paying for it with `broadcast` everywhere, and `signal`-on-one-condvar is subtly broken.**

- **One condvar + `signal` — WRONG (latent deadlock).** Scenario, capacity = 1: consumers C1, C2 blocked (queue empty), producer P1 blocked is impossible yet, but take: queue **full**, producers P1, P2 blocked on the shared cv; C arrives, removes the item, `signal(cv)` — suppose the implementation happens to wake... fine. Now the classic failing case: queue **empty**; C1 and C2 wait on cv. P puts an item, `signal(cv)`, wakes C1. C1 takes the item and — having made `not_full` "true" — does `signal(cv)`. But no producer is waiting; the signal lands on **C2**, whose predicate `count > 0` is false; C2 re-sleeps (thanks to `while`, no corruption). Now suppose simultaneously the queue interleaves so that a producer *was* also waiting alongside C2 (mixed waiter set — capacity full earlier, drained, refilled...): a signal meant for a producer can be absorbed by a consumer that just re-sleeps, and the producer that could have progressed waits forever while its wakeup quota was burned. All threads blocked, work available ⇒ deadlock. The `while` loop protects *state integrity* but cannot conjure back a misdelivered wakeup.
- **One condvar + `broadcast` on every state change — correct but herd-y.** Every `put`/`get` wakes all waiters of both roles; the `while` loops filter. Safe (this is exactly why the loop discipline is written to survive broadcast), and acceptable for low contention or where the language gives you only one monitor (classic Java `synchronized`/`wait`/`notifyAll` — the textbook reason Java code must use `notifyAll` with a single monitor). Under load it's O(waiters) wasted switches per operation.
- **Two condvars + `signal` — correct AND efficient.** Because each condvar's waiter population is homogeneous (all waiting on the same predicate), `signal` can never misdeliver across roles; and because each queue op enables at most one opposite-role waiter, one `signal` is exactly the right dose. This is the standard, and the right answer here.

(For completeness: two condvars is also what lets you keep `signal` when you later add features — timeouts via `pthread_cond_timedwait` (predicate loop unchanged: `while (!P) { if (timedwait(...) == ETIMEDOUT && !P) return TIMEOUT; }` — re-check P even on timeout, the item may have arrived in the race), and close/shutdown via `broadcast` on both.)

## 8. Summary of the discipline (checklist form)

1. One mutex guards all queue state; no state access outside it.
2. One condvar per distinct predicate: `not_full` ⇔ `count < capacity`, `not_empty` ⇔ `count > 0`.
3. Wait pattern, always: `lock; while (!P) wait(cv, m); ...act, P guaranteed...; signal(other_cv); unlock;`
4. `while` not `if`: wakeup is a hint; the predicate under the mutex is the truth (Mesa semantics, stolen wakeups, spurious wakeups, broadcast overshoot).
5. Lost wakeups are impossible because (a) predicate test and state mutation are serialized by `m`, and (b) `cond_wait` releases `m` and sleeps atomically — the test→sleep window is closed.
6. `signal` when one event enables ≤ 1 waiter of a homogeneous waiter set; `broadcast` for shutdown, bulk/multi-enable events, or any heterogeneous waiter set. Code must stay correct if `signal` behaves like `broadcast`.
7. Two condvars, not one: with one, `signal` can deliver a wakeup to a thread of the wrong role and deadlock the system despite available work; one-condvar designs are forced into `broadcast` (thundering herd) to be safe.
