# q5 — fable-raw (archetype: systems-tradeoff)

## Task

A single hot counter (e.g. a like-count on a viral item) is receiving very high concurrent increments across many app servers. Analyze the trade-off between (a) a single-row atomic UPDATE in Postgres, (b) Redis INCR, and (c) sharded/approximate counters (N sub-counters summed on read). Derive analytically how throughput and read-accuracy scale with contention for each, state the crossover points and the assumptions behind them, and recommend a policy that is correct under a Redis outage. Show the reasoning, not just a conclusion.

## Fable answer

# Hot Counter Under High Concurrency: Postgres UPDATE vs Redis INCR vs Sharded Counters

## 0. Model and assumptions

Let:

- `λ` = aggregate offered increment rate (ops/s) across `M` app servers, all targeting **one logical counter**
- `S` = service time the counter's serialization point is *held* per increment
- `ρ = λ·S` = utilization of that serialization point
- Reads happen at rate `λ_r`, and "accuracy" = |displayed − true committed count| at read time (absolute), or that divided by the true count (relative)

Hardware assumptions used for the numbers below (stated so you can re-derive with your own): in-memory tuple update + WAL insert ≈ 10–20 µs; fsync ≈ 100–500 µs local NVMe/SSD, 0.5–2 ms cloud block storage; scheduler wakeup/lock handoff ≈ 5–50 µs; Redis command processing ≈ 1–10 µs/op with the event loop able to sustain ~10⁵–10⁶ ops/s per instance; network RTT app→datastore ≈ 0.2–1 ms.

The key structural fact for all three options: **a single logical counter is a serialization point**. The three designs differ in (1) how expensive one pass through that point is, (2) whether the point can be split, and (3) what the failure semantics do to the count.

---

## 1. (a) Single-row atomic `UPDATE ... SET n = n + 1` in Postgres

### Throughput derivation

The subtle point most analyses miss: **Postgres holds the row-level exclusive lock until COMMIT, not until the end of the UPDATE statement.** So if each increment is its own transaction (the normal web-app case), the lock hold time is:

```
S_row = t_update (tuple + WAL insert, in memory)  ~ 10–20 µs
      + t_commit                                   (depends on synchronous_commit)
      + t_handoff (wake next waiter)               ~ 5–50 µs
```

- With `synchronous_commit = on` (default, durable): `t_commit` includes the WAL flush. Group commit does **not** help here — group commit amortizes fsync across *concurrent* committers, but transactions queued on the *same row* are not concurrent; they commit one after another. So `S_row ≈ 0.15–2 ms` and the ceiling is

  **`λ*_a = 1/S_row ≈ 500 – 5,000 increments/s`** (≈1–2k/s on typical cloud storage).

- With `synchronous_commit = off` (bounded-loss mode): `S_row ≈ t_update + t_handoff ≈ 20–70 µs`, ceiling **≈ 15k–50k/s** — but see the degradation term below.

Queueing behavior as contention rises: treating the row as an M/D/1 server, mean queue wait `W ≈ ρ·S/(2(1−ρ))`. Latency is fine at ρ=0.5, doubles by ρ=0.7, and diverges hyperbolically as ρ→1. This matters operationally more than the raw ceiling: each waiter **is a Postgres backend holding a pooled connection**. At λ = λ*, the waiter count grows without bound → connection pool exhaustion → *unrelated* queries stall. A hot row doesn't just cap the counter; it can melt the whole database tier. Design threshold: keep `λ ≤ ~0.5–0.7 / S_row`.

**Non-stationary ceiling (MVCC bloat).** Every increment writes a new tuple version and leaves a dead one. λ dead tuples/s on one hot page: HOT updates keep this on-page while there's free space, and single-page pruning cleans up opportunistically, but under sustained multi-kHz pressure the page fills, updates go non-HOT, index entries churn, version chains lengthen, and `t_update` itself grows → **throughput degrades over time**, a positive feedback loop. Mitigation (`fillfactor ≈ 50` on the counter table, aggressive autovacuum) delays but doesn't remove this. So the honest statement is: `λ*_a` is 1–2k/s durable **and decaying under sustained load**.

### Accuracy

Exact, always. MVCC readers never block on writers; a `SELECT` sees the last committed value. Error = 0, independent of λ. This is the option's entire virtue.

## 2. (b) Redis INCR

### Throughput derivation

Redis is a single-threaded event loop; `INCR` is O(1) on an in-memory integer. There is **no per-key contention penalty at all** — every command on the instance serializes through the loop anyway, so a hot key is indistinguishable from spread keys until the *instance* saturates:

**`λ*_b ≈ instance command budget ≈ 10⁵–10⁶ ops/s`** (per-connection rate is RTT-bound at `1/RTT ≈ 1–5k/s`, so you need many connections or pipelining to reach it).

Two caveats that bound this in practice:

1. **Redis Cluster does not shard a single key.** One hot key lives on exactly one node; adding cluster nodes adds zero capacity for it. Past ~several 100k/s on one key you are forced into option (c) at the Redis layer anyway (client-side sharded keys `cnt:{item}:0..N-1` — deliberately *without* hash tags so they land on different nodes, which means the summing `MGET` must be split per node).
2. Bandwidth/CPU of that one node is shared with everything else on it; a viral key can starve co-tenants ("hot shard" problem).

### Accuracy — the part that's usually glossed over

Redis reads are exact *with respect to acknowledged increments*, but the acknowledged count and the true count diverge under failures, and the divergence **scales linearly with λ**:

| Failure | Count error |
|---|---|
| Crash with AOF `everysec` | lose up to `λ × 1 s` increments (at λ=100k/s: 100k likes) |
| Crash with RDB only | lose `λ × minutes` |
| Failover (async replication) | lose `λ × replication lag` |
| Client timeout + naive retry | **overcount** ≈ `λ × P(ambiguous outcome)` — INCR is not idempotent, and a timed-out INCR may or may not have applied |

So "Redis is exact" is only true in the failure-free path. Its steady-state error is 0 but its **incident error is Θ(λ)**, unbounded in advance unless you bound it architecturally (§5). Note the symmetry: Postgres with `synchronous_commit=off` has loss window ≈ 3×`wal_writer_delay` (~600 ms default) — i.e., async-commit Postgres is in the **same durability class as AOF-everysec Redis**, just 10–50× slower. That's a fair like-for-like comparison; comparing durable-PG throughput against volatile-Redis throughput is the classic apples-to-oranges benchmark sin.

## 3. (c) Sharded / approximate counters

### Throughput derivation

Split the counter into `N` sub-counters; each increment picks one (random, or hash of server/thread id — random gives per-shard rate `λ/N` with binomial fluctuation; per-server hashing gives cache locality but risks imbalance). Per-shard utilization drops to `ρ/N`, so:

```
λ*_c(N) = min( N × 0.7/S_row ,   ← per-shard serialization, keep ρ_shard ≤ 0.7
               X_wal_group,       ← shared WAL flush bandwidth
               X_cpu, X_conn )    ← per-node resources
```

Crucially, sharding **restores the benefit of group commit**: transactions on *distinct* rows can overlap and flush together, so the WAL term is `K/t_fsync` (K = txns per flush group) ≈ 10⁵/s-scale, far above the single-row ceiling. Throughput is ~linear in N until a shared resource binds — in Postgres typically CPU/connections at tens of thousands of TPS, in Redis the per-node loop.

Choose **`N = ceil(λ_peak × S_row / 0.7) × safety(≈2)`**. Example: λ_peak = 20k/s durable PG, S_row = 0.5 ms → N ≥ 29 → use 64. Implementation detail that actually matters: put shards on **separate heap pages** (fillfactor, or padding), otherwise you've traded row-lock contention for buffer content-lock contention on one page and gained less than N×.

Diminishing returns: reads cost O(N), and N beyond ~64–256 buys little because you've hit the shared-resource terms anyway.

### Accuracy derivation

- **Sum-on-read in one Postgres transaction**: MVCC gives a consistent snapshot across all N rows → the sum is *exact at a point in time*. Sharding in PG costs **zero accuracy**. (Underrated property.)
- **Sum across Redis nodes / non-snapshot reads**: the N GETs happen over a time spread `t_spread`; the sum corresponds to no single instant, skew bounded by `λ × t_spread` (small: ~λ × few ms).
- **Cached sum with TTL τ** (you will want this — O(N) reads at high `λ_r` are wasteful): staleness ≤ `λ × τ` absolute. Relative error = `λτ / C(t)`; since a viral counter's total C grows ∝ λ·t, relative staleness ≈ `τ / age` — after 10 minutes with τ=1 s, ≤0.2%, imperceptible.
- **Buffered/approximate variant** (per-app-server in-memory accumulator, flushed every δ as `UPDATE ... SET n = n + $delta`): write rate to the store collapses from λ to `M/δ` statements/s **independent of λ** (M=200 servers, δ=1 s → 200 stmt/s — trivial even nearly unsharded). Cost: staleness ≤ λδ, and **crash loss ≤ one server's buffer = (λ/M)·δ**. This is the only design whose DB load is O(1) in λ; it's how every large-scale like-counter actually works.

## 4. Crossover points (with the assumptions that produce them)

Assumptions: durable writes wanted at the store of record; cloud SSD fsync ≈ 0.5 ms; design to ρ ≤ 0.7; 5× headroom for virality spikes (a counter that's hot is, by definition, one whose λ you failed to predict).

| Sustained λ (peak ÷ headroom) | Cheapest correct design | Why the previous one fails |
|---|---|---|
| < ~200–500/s | (a) plain PG row | — (this covers 99.9% of "hot" items; don't over-engineer) |
| ~500/s – ~10–20k/s | (c) N=16–64 sharded PG rows, snapshot-sum reads | single row hits `1/S_row`, waiter pileup exhausts pool, bloat decay |
| ~20k – ~200k/s | (b) Redis INCR for display **+** (c)-buffered flush to PG for truth | even sharded PG binds on CPU/connections; per-write RTT×connections cost |
| > ~200–500k/s | client-sharded Redis keys + per-server buffering (b+c), or a log/stream aggregator (Kafka→rollup) | single Redis key = single node saturates; cluster can't split a key |

Accuracy scaling with contention, side by side:

- (a): error **0**, independent of λ — pays for it with a hard, decaying throughput ceiling and blast-radius risk.
- (b): error 0 in steady state; **incident error Θ(λ × loss-window)**, plus Θ(λ × p_timeout) overcount if retries are naive.
- (c): error bounded and *chosen by you*: ≤ λτ (read cache) + λδ/M per crashed server (buffering); with PG snapshot sums and no buffering, exactly 0.

One more honest reframing: if a "like" is unique per user, the counter is really `|{users who liked}|` — a set cardinality, not an integer. That makes an idempotent per-user ledger (below) the *natural* representation, and makes INCR-style counting structurally prone to drift (retries, un-likes). Exact dedup requires the ledger; HyperLogLog is only relevant if approximate distinct-count were acceptable (for likes it usually isn't, since un-like must decrement).

## 5. Recommended policy — correct under a Redis outage

**Principle: Redis is a derived cache, never the system of record.** Any design where the authoritative count exists only in Redis is *not correct under outage*, full stop: crash/failover loses an unknowable delta, and ambiguous INCRs make the surviving value untrustworthy in both directions. The common anti-patterns to reject explicitly:

- ✗ "INCR in Redis, cron persists the value to PG" — outage loses the un-persisted delta and you can't tell how much.
- ✗ Dual-write (PG + Redis, both authoritative) without an outbox — they silently diverge; you now have two wrong numbers.

### The policy

**Source of truth (Postgres), write path:**
1. Each like is an **idempotent ledger insert**: `INSERT INTO likes(item_id, user_id) ... ON CONFLICT DO NOTHING`. Insert-only, no hot row; retries are safe (idempotence solves the ambiguous-outcome problem *by construction*, which no counter representation can). Index the unique key in an order that avoids rightmost-leaf pileup for one item (e.g., `(item_id, user_id)` is fine since user_id spreads within the item).
2. A **single-writer rollup job** (or per-shard writers) periodically folds new ledger rows into `item_counts` — one writer per shard ⇒ zero contention on the materialized counter, and it also handles un-likes. If write rates exceed what ledger inserts can take, interpose per-app-server buffers with δ ≈ 0.5–1 s flushes (accepting loss ≤ (λ/M)·δ per server crash, or WAL the buffer locally if even that is unacceptable — state which you chose).

**Display path (Redis as accelerator):**
3. Redis holds the display value. App servers `INCR` it **fire-and-forget behind a circuit breaker** for real-time feel; the value is periodically **overwritten** (`SET`, with an epoch tag) from the PG rollup, so any INCR drift (retries, missed increments during blips) is bounded by one refresh interval and then corrected. Redis errors never fail the user request.

**Under Redis outage (the correctness argument):**
4. Writes are unaffected — the ledger is PG. **Nothing is lost.**
5. Reads fall back to `item_counts` (+ optionally the recent ledger delta), fronted by **request coalescing / single-flight** so the stampede of display reads becomes ~1 PG read per item per second, not λ_r. Displayed value is stale by ≤ rollup interval — degraded freshness, never wrong data.
6. **Recovery:** never trust the surviving/replica Redis value. Repopulate with `SET` from PG, epoch-guarded so a late INCR from the old epoch can't resurrect a stale count. Clamp the *displayed* value per item to max-seen (or rely on the epoch) so users never watch the count go backwards across a failover.

**Why this dominates:** it takes (a)'s exactness where it belongs (system of record, via an idempotent representation immune to hot-row contention), (b)'s throughput where it belongs (display path, where an error bounded by one refresh interval is invisible), and (c)'s O(1)-in-λ database load (buffered/rolled-up writes) — while making the Redis outage a *freshness* incident instead of a *correctness* incident. The residual approximations are explicit and bounded: display staleness ≤ refresh interval + λτ, and (only if you enabled server-side buffering) crash loss ≤ (λ/M)·δ per failed server.
