# q1 — fable-raw (archetype: code-design)

## Task

Design a multi-tenant API rate limiter that must be FAIR across tenants with wildly different traffic volumes (some 10 req/s, some 10k req/s), degrade gracefully when the shared Redis backend is unavailable, and avoid BOTH per-tenant starvation AND global thundering-herd on limit reset. Specify: the data structures, the exact algorithm for allow/deny, the fairness mechanism, the Redis-outage failure semantics, and the THREE subtlest correctness pitfalls someone implementing this would most likely get wrong (with why). Be concrete and rigorous.

## Fable answer

# Multi-Tenant Fair Rate Limiter — Design

## 0. Architecture in one paragraph

N stateless gateway nodes enforce limits by calling a single atomic Lua script against a shared Redis (Cluster). The admission algorithm is **GCRA (Generic Cell Rate Algorithm)** per tenant — one float of state, continuous refill, so there is *no window boundary and therefore no reset instant to herd on*. Cross-tenant fairness is **not** done in the hot path: a low-frequency **water-filling controller** computes weighted max-min fair ceilings from *offered* demand and pushes them to nodes; the hot path enforces `min(configured_rate, fair_ceiling)` with a single-key atomic script. On Redis outage, each node degrades to a local monotonic-clock GCRA at `guaranteed_rate / N`, which keeps the aggregate below cluster capacity and preserves every tenant's floor (fail-degraded, neither fail-open nor fail-closed).

---

## 1. Data structures

**Redis (all tenant keys use hash-tag `{T}` so they share a cluster slot):**

| Key | Type | Contents | TTL |
|---|---|---|---|
| `rl:{T}:tat` | string (float, µs) | GCRA Theoretical Arrival Time | `≥ tat − now` (see Pitfall 3c) |
| `rl:{T}:demand` | hash | `slot:<epoch-sec> → offered cost` (2–3 rolling 1s slots) | 3 s |
| `rl:{T}:cfg` | hash | `rate r_T, burst b_T, weight w_T, guarantee g_T, max_ceiling` | none |
| `rl:alloc` | hash | tenant → effective ceiling `c_T` (+ version) | none (controller-owned) |
| `rl:node:<id>` | string | heartbeat | 3 s |
| `rl:tenants` | set | tenant registry for controller SCAN-free iteration | none |

**Per gateway node (in memory):**

- Read-through caches of `cfg` and `rl:alloc` (TTL ~1 s + pub/sub invalidation, refresh jittered ±20%).
- **Shadow local GCRA state per tenant** (`tat_local` on the **monotonic** clock), maintained continuously even while Redis is healthy, so failover starts warm.
- Circuit breaker per Redis shard (Cluster: per slot-range, so a partial outage only degrades tenants on dead slots).
- Cached live-node count `N_live` from heartbeat keys, **frozen at last-known value when the breaker opens**.

State cost: O(1) per tenant (~120 bytes in Redis). Hot path: exactly 1 `EVALSHA` per request.

---

## 2. Exact allow/deny algorithm

### 2.1 Node-side (per request, cost `c ≥ 1`)

```
cfg  = cache.cfg(T)                       # miss → Redis; miss during outage → conservative default (1 rps)
ceil = cache.alloc(T) or cfg.rate         # fairness ceiling, may be stale ≤ 1s
r    = min(cfg.rate, ceil);  Tint = 1e6 / r  (µs/token);  b = cfg.burst
if c > b: return 400 "cost exceeds burst"          # NOT 429 — no Retry-After can ever satisfy it
if breaker.closed:
    res = EVALSHA(gcra, keys=[rl:{T}:tat, rl:{T}:demand], argv=[Tint, b, c, ...])
    on error/timeout(5ms): breaker.record_fail(); goto LOCAL
    also feed the decision into the shadow local bucket (keep it warm)
    return res
LOCAL:  # outage mode, §4
    r_local = cfg.g_T / N_frozen;  local monotonic-clock GCRA at (r_local, b·g_T/(r·N_frozen))
```

### 2.2 Redis Lua (atomic; effects-replication)

```lua
-- KEYS[1]=rl:{T}:tat  KEYS[2]=rl:{T}:demand
-- ARGV[1]=Tint(µs/token) ARGV[2]=burst b ARGV[3]=cost c
redis.replicate_commands()                    -- required before TIME on old Redis; default ≥5
local t   = redis.call('TIME')
local now = t[1]*1000000 + t[2]               -- single time authority: Redis, not the caller
local Ti  = tonumber(ARGV[1]); local b = tonumber(ARGV[2]); local c = tonumber(ARGV[3])

-- (A) demand accounting: OFFERED load, incremented BEFORE the decision (Pitfall 1)
local slot = math.floor(now/1000000)
redis.call('HINCRBY', KEYS[2], slot, c);  redis.call('PEXPIRE', KEYS[2], 3000)

local tat = tonumber(redis.call('GET', KEYS[1])) or now
if tat < now then tat = now end               -- idle credit accrues, capped by burst below
local new_tat = tat + c*Ti
if new_tat - now <= b*Ti then                 -- debt after admission fits within burst
    local ttl = math.ceil((new_tat - now)/1000) + 60000   -- covers full TAT horizon (Pitfall 3c)
    redis.call('SET', KEYS[1], new_tat, 'PX', ttl)
    return {1, math.floor((b*Ti - (new_tat - now))/Ti), 0}      -- allow, remaining, 0
else
    local retry = (tat + c*Ti - b*Ti) - now   -- computed from UNMODIFIED tat (Pitfall 2a)
    return {0, 0, retry}                      -- deny; state untouched
end
```

Properties: exactly `b` requests admitted from cold in one instant; steady-state rate exactly `r`; **refill is continuous**, so quota "reset" as a synchronized event does not exist — the classic top-of-minute thundering herd is eliminated by construction, not by jitter band-aids.

Node adds `Retry-After = ceil((retry + U(0, c·Ti))/1e6)` — jittered, see Pitfall 2b — plus `X-RateLimit-Limit/Remaining/Reset`.

## 3. Fairness mechanism (weighted max-min, no starvation)

Every tenant has a **guarantee** `g_T > 0` with `Σ g_T ≤ 0.7·C` (C = protected cluster capacity) and a weight `w_T`. Every Δ = 500 ms, a controller (leader via `SET NX PX` lease with fencing version; computation is deterministic so a brief dual-leader episode is last-writer-wins-safe):

1. Reads `rl:{T}:demand` for tenants in `rl:tenants`, computes EWMA offered demand `d_T` (α ≈ 0.3).
2. Excess demand `e_T = max(0, d_T − g_T)`; pool `P = C − Σ g_T`.
3. **Water-filling**: find λ s.t. `Σ min(e_T, w_T·λ) = P`; ceiling `c_T = min(cfg.max_ceiling, g_T + min(e_T, w_T·λ))`.
4. **Slew-rate limit**: `c_T` may at most double per interval on the way up (Pitfall 2b, macro-herd damping); drops apply immediately.
5. `HSET rl:alloc` + `PUBLISH rl:invalidate`.

Why this is fair and starvation-free:
- A 10 req/s tenant's demand sits below the water level → it *always* receives its full demand; the 10k req/s tenant absorbs all of the throttling. That is exactly max-min fairness.
- Under total overload every tenant still holds `g_T > 0` — a hard floor independent of anyone else's behavior.
- Max-min is demand-exaggeration-resistant: reporting demand above the water level does not raise your allocation, so a flooding tenant cannot distort the allocation of others.
- Bounded overshoot: enforcement of `c_T` lags demand by ≤ Δ + cache TTL, so aggregate can exceed C by at most `Σ(ceiling raises) × ~1.5 s`. This is why C must be set with 10–20% headroom below true capacity — the design deliberately trades hot-path cross-key atomicity (impossible across Cluster slots anyway) for an asynchronous, *boundedly*-stale global constraint.

At the 10k req/s end, one EVALSHA per request is ~10k ops/s per hot tenant — fine for Redis (>100k ops/s/shard). If Redis CPU or RTT becomes the limit, add **token leasing** (a node leases batches of `n = max(1, r·RTT·2)` admissions per tenant, lease TTL ~200 ms): amortizes round trips at the price of ≤ `N·n` admission slack per tenant, which must be counted inside the burst budget — and unused leases must simply expire, never be "returned" (the return path races with re-lease and double-credits).

---

## 4. Redis-outage failure semantics (fail-degraded)

- **Detection**: 5 ms hard timeout on EVALSHA; breaker opens on 10 consecutive failures or >50% errors over 2 s. A *slow* Redis is treated as a *down* Redis — the limiter may never become the availability bottleneck.
- **While open**: each node enforces local GCRA per tenant at `g_T / N_frozen` (`N_frozen` = last healthy heartbeat count; a node that boots mid-outage assumes configured max fleet size — conservative). Worst-case aggregate admitted = `Σ g_T ≤ 0.7·C` even if all nodes are partitioned from Redis simultaneously → the backend is protected. Every tenant keeps its floor → no starvation during the outage. Explicit, documented trade-off: big tenants lose burst/borrowed headroom during outages; small tenants (demand < guarantee) feel nothing.
- **Unknown tenant during outage** (cfg cache miss): fail-closed to a 1 req/s default bucket. Untrusted growth doesn't get free rein exactly when observability is degraded.
- **Recovery**: half-open with *one* probe per node per 500 ms (request coalescing — never one probe per user request), then **jittered rejoin** over U(0, 5 s) per node so a cold/recovering Redis is not hit by N nodes × full traffic at the same millisecond (thundering herd *on recovery* is as real as on reset). Local state is discarded, **never merged back**: GCRA's `max(tat, now)` makes the authoritative state self-forgiving — replaying outage-time admissions into Redis would double-count and cause a deny storm.
- **Partial outage** (some Cluster slots down): per-slot breakers; only tenants hashed there degrade.

---

## 5. The three subtlest pitfalls

**Pitfall 1 — Feeding the fairness controller *admitted* load instead of *offered* load (starvation lock-in).**
If `d_T` is measured from allowed requests, a throttled tenant's measured demand equals its current ceiling. Water-filling then concludes "demand satisfied" and never raises that ceiling, while capacity freed elsewhere flows to tenants that happen to hold high ceilings. The system freezes into whatever allocation existed at the first overload — a hysteresis trap that looks like correct behavior in every unit test (each component is "working") and only appears as slow, permanent unfairness in production. That is why the `HINCRBY` in the script executes **before** the allow/deny branch, on the deny path too. Related second-order trap: EWMA time constant vs. Δ — too slow and reallocation oscillates (capacity released a full second after a burst ends gets granted to a tenant that no longer wants it); damp with the ×2-per-interval slew limit.

**Pitfall 2 — Deny-path TAT semantics: both possible choices are wrong in one direction each, and you must know which wrongness you picked.**
(a) If deny *advances* TAT ("count denied traffic against the bucket"), a tenant offering 3× its rate accumulates unbounded future debt while receiving 0% throughput; when it slows back to a compliant rate it stays locked out (TAT is minutes in the future), and anyone who merely *knows* a tenant's API key can DoS it for free with rejected requests. So deny must leave state untouched — as in the script. (b) But *because* deny leaves state untouched, every request denied in the same instant receives the **identical** `retry` value → they all come back in the same millisecond, get denied together, and recohere forever: a self-sustaining per-tenant micro-herd that continuous refill does *not* fix. The fix is deliberate desynchronization: server-side jitter `U(0, c·Ti)` on Retry-After, plus the controller's slew-limited, phase-jittered ceiling raises so that after a global squeeze all tenants don't regain headroom in the same control tick (the macro version of the same herd).

**Pitfall 3 — Time authority, replication, and debt-forgiving TTLs (three coupled clock bugs).**
(a) Passing gateway wall-clock time into the script: with N nodes and skew s, a fast-clock node silently grants extra burst (`s/Ti` tokens) and a slow one emits negative Retry-After; use `redis.call('TIME')` — one clock for one datum. (b) Doing so makes the script non-deterministic, which is only safe under **effects replication** (`redis.replicate_commands()`; default on Redis ≥ 5) — under verbatim script replication the replica re-executes with a *different* `now` and the TAT diverges. Also accept that failover to an async replica loses the last moments of TAT advancement: burst amplification ≈ `rate × replication_lag`, which is another reason C carries headroom — don't pretend exactly-once. (c) TTL: setting the key TTL to "the window" (e.g., 1 s) instead of `≥ tat − now` means a tenant that overdrafts with a high-cost request and then goes idle for TTL gets its entire debt expired — a pause-to-reset exploit that inverts the limiter for exactly the bursty clients it exists to police. TTL must cover the full TAT horizon (the script computes it per write). And in the local fallback path, use the **monotonic** clock: an NTP step during a Redis outage (when you have no authority to cross-check) otherwise spuriously refills or freezes every local bucket at once.

*Honorable mentions (excluded from the top three because they're better-known):* GET-then-SET instead of one Lua script (over-admission ∝ concurrency); trying to check tenant-key + global-pool atomically across Cluster slots (impossible — the async-ceiling architecture exists precisely to avoid needing it); refunding cost on downstream failure (the refund races with concurrent admissions and is gameable — don't, or cap it); `cost > burst` returning 429 with an unsatisfiable Retry-After instead of 400.
