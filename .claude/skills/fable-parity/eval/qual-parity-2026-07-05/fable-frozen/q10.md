# q10 — fable-raw (archetype: systems-tradeoff)

## Task

For an order-management system that needs full history, temporal ('as-of') queries, and audit compliance, analyze event sourcing vs CRUD-with-an-audit-log. Derive the trade-offs on: query complexity for current-state vs historical, storage growth, consistency/rebuild risk, schema-evolution pain, and operational complexity. State the crossover conditions (when each is the right call) and give a concrete recommendation with its assumptions.

## Fable answer

## Event Sourcing (ES) vs CRUD + Audit Log for an Order-Management System

### Framing and a necessary precision

The comparison is only fair if we pin down what "CRUD + audit log" means, because there are three materially different variants, and the trade-offs differ:

- **(A) Application-level audit log**: app code writes the audit row in the same transaction as the mutation. Vulnerable to code paths that forget, and to any out-of-band write (ops SQL, migration script, bulk import).
- **(B) Database-enforced audit**: triggers, CDC (Debezium/logical decoding), or **SQL:2011 system-versioned temporal tables**. Captures *every* mutation regardless of code path; temporal tables give you `FOR SYSTEM_TIME AS OF` queries natively.
- **(C) Audit log in a separate store written asynchronously**: has a dual-write problem — the audit trail can silently diverge from the truth. **Disqualified for compliance**; I won't consider it further.

Event sourcing means: the **event log is the system of record**; current state is a fold over events; read models are derived projections. The key structural difference from all CRUD variants: in ES the history *is* the truth; in CRUD the history is a *byproduct* of the truth, and the guarantee that the byproduct is complete and faithful is exactly what audit compliance depends on.

---

### 1. Query complexity: current state vs historical

**Current-state queries**
- **CRUD**: trivial. `SELECT ... FROM orders WHERE id = ?`. One table, indexable, joinable, transactionally consistent with the write. This is CRUD's home turf.
- **ES**: current state requires either replaying the stream (O(events) per aggregate — fine per-aggregate with snapshots, terrible for cross-aggregate queries like "all orders shipped to region X over $500") or maintaining **projections** (CQRS read models). Projections restore SQL-grade query power but introduce: projection code to write and maintain, **eventual consistency between write and read side** (read-your-own-writes must be engineered — e.g., version-pinned reads, or synchronous in-transaction projections if you accept coupling), and a second schema to evolve.
- Edge case: uniqueness and cross-aggregate invariants ("one open order per cart", "reserve stock") are *easy* in CRUD (unique index, row lock) and genuinely awkward in ES (reservation sagas, or a small consistent lookup table on the side — which is a CRUD island inside your ES system).

**Historical / as-of queries**
- **ES**: structurally native. "State of order 123 as of 2026-03-01T14:00Z" = fold events with `recorded_at <= t`. "Why is this order in state X" = read the stream; the *causal narrative* (who did what, in what order, with what intent — `OrderDiscountApplied{reason: retention_offer}`) is first-class. Arbitrary *new* historical questions ("how often did orders go shipped→refunded within 24h, over the last 3 years?") are answerable retroactively by replaying into a new projection — CRUD cannot answer questions its audit schema didn't anticipate capturing.
- **CRUD (A)**: as-of queries mean reconstructing state from diff rows — painful, and only as good as the diff granularity (field-level vs whole-row vs "user X edited order").
- **CRUD (B, temporal tables)**: `FOR SYSTEM_TIME AS OF` gives clean point-in-time *row state* with ordinary SQL, including joins across temporal tables. This closes most of the as-of gap. What it does **not** give you: **intent/causality** (you see the row changed from `status=pending` to `status=cancelled`; you don't see *cancelled-by-customer-due-to-delay* vs *cancelled-by-fraud-system* unless you add columns for it — at which point you're hand-rolling event semantics), and it records *transaction time* only.
- **Bitemporality edge case**: "as of" is ambiguous — *what we knew at time T* (transaction time) vs *what was true at time T* (valid time, e.g., a backdated price correction). Neither pattern gives you valid time for free. ES handles retroactive corrections more idiomatically (compensating/correction events with both timestamps, projections interpret them); temporal tables need explicit `valid_from/valid_to` application-time period columns and much more careful query discipline. If your compliance regime requires "reproduce exactly the invoice we would have generated on date D", check whether you need one or both time axes **before** choosing.

**Verdict**: CRUD wins current-state decisively; ES wins historical decisively, with temporal tables narrowing (not closing) the gap — they replay *state*, not *meaning*.

---

### 2. Storage growth

- **CRUD+audit**: hot table stays O(entities); audit/history table grows O(mutations). Row-image auditing (temporal tables store full before-images) can be *larger* than an event log for wide rows with frequent small changes — a 60-column order row versioned on every status flip stores 60 columns per flip, where ES stores one small `OrderStatusChanged` event. Field-diff audit logs are compact but expensive to reconstruct from.
- **ES**: log grows O(events), append-only, compresses well, tiers well (old segments → cheap object storage). But total footprint = log + snapshots + **every projection** (each is a full materialized copy of some slice of state). With 3–5 projections, ES total storage often exceeds CRUD+audit.
- Orders are a favorable ES workload: aggregate streams are naturally short and bounded (an order accumulates ~10–50 events then goes quiescent forever). The pathological ES storage case — unbounded hot streams (accounts with millions of events) — mostly doesn't apply. Snapshotting is cheap and rarely even necessary.
- **Retention/deletion edge case (critical)**: GDPR/APPI erasure vs immutable log is a real conflict. ES answers: **crypto-shredding** (per-subject encryption keys, delete the key) — works but adds key-management infrastructure and makes "replay from history" partially lossy afterward; or stream rewriting, which is operationally ugly and undermines the audit claim. CRUD answers: delete/anonymize rows in hot + audit tables — straightforward, but hard-deleting audit rows may itself violate the *other* compliance requirement. Both patterns face the tension; ES's crypto-shredding is the more principled resolution but the more expensive to build. Budget for this either way.

**Verdict**: roughly a wash for order-shaped data; ES trends higher total footprint (projections) but cheaper cold tiering; the differentiator is the deletion story, not gigabytes.

---

### 3. Consistency / rebuild risk

- **CRUD (A/B)**: state and history live in one ACID database; a single transaction covers both (variant B enforces it structurally). No rebuild concept — the current table *is* the truth. Failure mode: **audit incompleteness**, not state inconsistency. With variant A, one forgotten code path or one ops `UPDATE` and your audit trail has a hole you may discover only during the audit. Variant B (triggers/temporal) eliminates this for in-database changes. Second failure mode: history is *lossy by construction* — if the audit schema didn't capture a field or the actor identity, that information is gone forever; you can't retro-capture.
- **ES**: the log is the single source of truth — state/history divergence is *impossible by construction*, which is the strongest possible audit posture ("the audit trail cannot disagree with the system state because it *is* the system state"). New risks appear instead:
  - **Projection lag/failure**: read models are eventually consistent; a stuck projector means stale reads. Needs monitoring (lag metrics), idempotent handlers (at-least-once delivery ⇒ dedupe by event position), and a rebuild runbook.
  - **Rebuild cost**: full projection rebuild is O(total events). At, say, 10M orders × 20 events, replaying 200M events at 20–50k events/s is 1–3 hours — fine if you can rebuild side-by-side and cut over, dangerous if your only copy of a critical read model is down meanwhile. Mitigations: parallel-by-stream replay, blue/green projections, checkpointed rebuilds.
  - **Replay determinism (the subtle one)**: replay must be pure. Any projector that calls `now()`, reads external services, or — worst — **triggers side effects (emails, payment captures) during replay** corrupts rebuilds or spams customers. Requires disciplined separation of projections (pure, replayable) from process managers/sagas (effectful, checkpoint-guarded, never re-run past their checkpoint). This is the discipline teams most often get wrong.
  - **Buggy fold ≠ safe**: a bug in the fold/projection gives wrong *state* even though events are correct. Upside: fix the code, replay, and the state heals — CRUD has no equivalent "recompute truth from first principles" escape hatch; a buggy CRUD write is permanent unless the audit log happens to contain enough to reverse it.

**Verdict**: CRUD risk = *silent audit gaps* (mitigate with variant B); ES risk = *operational rebuild/lag incidents* (mitigate with runbooks and purity discipline). For compliance specifically, ES's failure modes are loud and recoverable; CRUD-A's are silent and unrecoverable. CRUD-B sits in between.

---

### 4. Schema evolution

- **CRUD**: one schema, standard migrations (`ALTER TABLE`, backfill). Mature tooling, one-shot cost. Pain points: audit-table migrations for *historical* rows are awkward (what does the new NOT NULL column mean for 2024 audit rows?), and temporal tables restrict certain DDL. But fundamentally: **you migrate data once and old shapes cease to exist**.
- **ES**: events are **immutable forever** — you cannot ALTER 2024's events. Every event version ever emitted must remain readable for the lifetime of the system. Strategies, in ascending invasiveness: additive-only changes with defaults (works ~80% of the time) → **upcasters** (v1→v2→v3 transformation chain applied at read/replay; chains grow monotonically) → new event type + deprecate old (handlers must support both indefinitely) → copy-transform stream migration (heavy, breaks the "immutable log" audit narrative and needs its own provenance record).
  - Semantic drift is nastier than shape drift: if the *meaning* of `OrderShipped` changed in 2025 (now emitted per-parcel, not per-order), every projection folding old+new events must encode business-rule history. This cost compounds with system age and team turnover.
  - And note: with CQRS you evolve **both** the event schema and each projection schema; projection schema changes at least have the escape hatch of drop-and-replay.
- Countervailing point: CRUD migrations are one-shot but can be *hard* one-shots (long locks on huge audit tables, backfill windows); ES additive evolution is deploy-and-forget with zero data migration. For teams that evolve the model *frequently but additively*, ES day-to-day evolution can actually feel lighter. The pain concentrates in the rare *breaking* change.

**Verdict**: clear CRUD win on worst-case evolution cost. ES's evolution pain is the tax you pay for immutability, it is permanent, and it grows with system age. Mitigate by keeping events **small, intention-named, and minimal** (don't serialize fat DTOs into events) and standing up upcaster + schema-registry conventions from day one, not after v3 of your first event.

---

### 5. Operational complexity

- **CRUD+audit**: one database. Backup/restore, PITR, replication, monitoring, and hiring are all commodity. Triggers or temporal tables add near-zero ops. On-call surface: the database.
- **ES+CQRS**: event store (dedicated like EventStoreDB/Axon, or Postgres-as-event-store — the latter reduces infra novelty at the cost of building append/subscription semantics yourself), subscription/dispatch infrastructure, N projection services with checkpoint state, snapshot management, rebuild tooling, lag dashboards, and backup consistency across log + read models (the log is the recovery source of truth; projections are rebuildable — which is elegant *if* the rebuild path is actually rehearsed). On-call surface: a distributed system.
- **The dominant hidden cost is people**: every future maintainer must understand aggregates, folds, projections, idempotency, and eventual consistency. Common failure pattern worth naming: teams adopt "event sourcing" but treat events as a change-feed while secretly trusting the read model as truth — yielding **the complexity of both patterns and the guarantees of neither**. If the team wouldn't confidently write an idempotent projector and a saga checkpoint today, that's a signal.
- Middle-ground note: CRUD + **transactional outbox** + CDC gives you an ordered event feed for integration/analytics *without* making the log the source of truth — often this captures 70% of what people actually wanted from ES at 20% of the ops cost.

**Verdict**: decisive CRUD win. ES ops cost is a step function, not a slope — you pay it even at small scale.

---

### Crossover conditions

**CRUD + DB-enforced history (variant B, ideally temporal tables + outbox/CDC) is the right call when:**
1. As-of requirements are about **state reconstruction** ("what did the order row look like on date D"), not causal narrative;
2. Audit compliance is satisfied by *complete, tamper-evident change capture* (temporal tables + restricted DB access + WORM export of the history satisfies most SOX/ISO/PCI-flavored audits);
3. Current-state, strongly consistent queries dominate the workload (typical order management: dashboards, fulfillment ops, customer service lookups);
4. Team is small/ordinary-skilled or the delivery timeline is tight;
5. Regulatory erasure (GDPR) applies and you can't fund crypto-shredding infrastructure.

**Event sourcing is the right call when at least two of these hold:**
1. Auditors/regulators require **intent and causality**, not just before/after images — "show that this refund was authorized by role R in response to event E" (finance-adjacent order flows, disputes/chargebacks, trading, healthcare orders);
2. You have concrete need to answer **historical questions not yet known** — retroactive analytics, ML feature backfill, "replay last quarter under the new fraud rules";
3. The domain is genuinely event-native with **complex order lifecycles** (partial shipments, amendments, compensations, long-running sagas across payment/inventory/shipping) where the state machine is the product;
4. You already need CQRS-grade read scaling or multiple heterogeneous read models (search index, analytics, ops dashboard), so projections were going to exist anyway — ES then adds the log for marginal cost;
5. Team has prior ES production experience or organizational commitment to acquire it.

Crossover in one sentence: **the moment the *reasons* for changes become audit deliverables — rather than the *fact* of changes — ES starts paying for itself; until then it's expensive insurance.**

---

### Recommendation

**Default recommendation: CRUD with database-enforced history — system-versioned temporal tables (or triggers where unavailable) on all order-domain tables, an explicit domain-events table written via transactional outbox in the same transaction as each mutation, and append-only/WORM export of history to cold storage for the audit trail.**

Concretely:
- Hot tables: `orders`, `order_lines`, `payments`, … with `SYSTEM_VERSIONING` → as-of queries via `FOR SYSTEM_TIME AS OF` with plain SQL joins.
- `domain_events(id, aggregate_id, type, actor, reason, payload, occurred_at)` written in-transaction (outbox pattern) → this captures the **intent** layer temporal tables lack, feeds CDC to analytics/search, and — decisively — is the migration on-ramp: if requirements later harden into "log must be the source of truth", you already have years of intent-bearing events and can promote them aggregate-by-aggregate without a big-bang rewrite.
- Audit hardening: DB roles that forbid direct DML on history, periodic hash-chained export to WORM object storage.
- Erasure: anonymize-in-place policy for both hot and history rows, documented for auditors.

**Assumptions this rests on** (each one, if false, moves the needle toward ES):
1. Compliance requires complete tamper-evident change history + actor attribution, **not** a regulator-mandated append-only source-of-truth ledger;
2. As-of queries are predominantly transaction-time state reconstruction; bitemporal (valid-time) requirements are absent or rare enough to handle with explicit period columns on the few tables that need them;
3. Workload is ordinary order-management scale (≤ ~10⁷ orders/yr, ≤ ~10³ writes/s peak) — a single well-tuned RDBMS with replicas suffices, so CQRS read-scaling pressure is absent;
4. Team is more fluent in relational modeling than in ES/CQRS operations;
5. Order lifecycles, while nontrivial, don't center on long-running compensating workflows where the event stream *is* the domain model.

If instead assumptions 1 or 5 fail — the audit deliverable is the causal event narrative itself, or the domain is saga-heavy — invert the call: **event-source the `Order` aggregate specifically** (short bounded streams, natural event vocabulary), keep reference/catalog/customer data in CRUD, run projections in the same Postgres to cap ops complexity, and adopt crypto-shredding for erasure from day one. Event-source the one aggregate that needs it; do not event-source the system.
