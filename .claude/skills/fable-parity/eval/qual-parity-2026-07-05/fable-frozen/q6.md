# q6 — fable-raw (archetype: code-design)

## Task

Design an idempotent webhook DELIVERY system (you are the sender): at-least-once delivery, exactly-once EFFECT on the receiver, retry with exponential backoff + jitter, and poison-message handling. Specify the dedup key and where it lives, the storage schema, ordering guarantees (and when ordering must be sacrificed), the retry state machine, and the THREE subtlest correctness pitfalls (e.g. dedup-window expiry vs late retries) with why each bites.

## Fable answer

# Idempotent Webhook Delivery System — Design Spec

## 1. Architecture (sender-side, transactional outbox)

```
Producer txn ──► events + deliveries rows (same ACID txn as business write)
                     │
Dispatcher(s) ──► claim due deliveries (lease) ──► HTTP POST ──► record attempt ──► succeed / reschedule / dead-letter
```

The outbox is the source of truth. Never publish from application memory ("write DB, then enqueue" loses events on crash between the two; "enqueue, then write DB" ghosts events). Everything downstream of the outbox is at-least-once; exactly-once **effect** is achieved only at the receiver via dedup — never claim exactly-once *delivery*, it does not exist over HTTP.

## 2. Dedup key — what it is and where it lives

- **Key:** `webhook_id` = the **event's** UUIDv7, minted once when the event row is created — **never per-attempt, never per-delivery-endpoint regenerated**. Every retry of the same logical event carries the identical `webhook_id`.
- On fan-out, the sender-side uniqueness unit is `(event_id, subscription_id)`; each receiver sees only its own stream, so `webhook_id` alone suffices on their side.
- **Wire format** (Standard-Webhooks style):
  - `Webhook-Id: <uuid>` (constant across retries)
  - `Webhook-Timestamp: <unix>` (fresh **per attempt** — see §7)
  - `Webhook-Signature: v1,HMAC-SHA256(secret, id + "." + timestamp + "." + body)` — signing the id means the receiver can trust the dedup key; an attacker can't replay a stale body under a new id or vice versa.
- **Where it lives:**
  1. Sender: `events.event_id` + `deliveries` (authoritative, retained ≥ retry horizon + replay window).
  2. Receiver: `processed_webhooks(webhook_id PRIMARY KEY, processed_at)` — the row **must be inserted in the same ACID transaction as the side effect** (§8-B). A Redis `SETNX` cache in front is an optimization only, never the correctness mechanism.
- **Receiver contract you must document:** on duplicate, return **2xx without re-executing** (respond as if it succeeded). Returning 409 for duplicates poisons the sender's state machine — the sender would classify a *successful* delivery as a hard failure and dead-letter it.

## 3. Storage schema (sender)

```sql
events(
  event_id        uuid PRIMARY KEY,          -- UUIDv7: time-ordered, is the dedup key
  topic           text NOT NULL,
  partition_key   text NOT NULL,             -- e.g. entity id, for per-key sequencing
  seq             bigint NOT NULL,           -- monotonic per partition_key (see §5)
  payload         jsonb NOT NULL,            -- frozen at creation; retries resend these exact bytes
  created_at      timestamptz NOT NULL,
  UNIQUE (partition_key, seq)
);

subscriptions(
  subscription_id uuid PRIMARY KEY,
  url text, secret bytea,
  ordered_mode    boolean DEFAULT false,
  consecutive_failures int DEFAULT 0,        -- endpoint-level circuit breaker
  paused_until    timestamptz,
  disabled_at     timestamptz
);

deliveries(
  delivery_id     uuid PRIMARY KEY,
  event_id        uuid REFERENCES events,
  subscription_id uuid REFERENCES subscriptions,
  state           text CHECK (state IN ('pending','in_flight','succeeded','dead')),
  attempt_count   int  DEFAULT 0,
  next_attempt_at timestamptz,               -- indexed with state: the work queue
  claimed_by      text,                      -- dispatcher instance id
  claim_expires_at timestamptz,              -- lease; crash recovery = lease expiry
  last_status_code int, last_error text,
  UNIQUE (event_id, subscription_id)         -- one logical delivery per endpoint
);
CREATE INDEX ON deliveries (state, next_attempt_at); -- claim query

attempts(                                    -- append-only audit; never updated
  delivery_id uuid, attempt_no int,
  started_at timestamptz, finished_at timestamptz,
  status_code int, outcome text, latency_ms int, response_snippet text,
  PRIMARY KEY (delivery_id, attempt_no)
);
```

Claim query (skips rows other workers hold, no lock contention):
```sql
UPDATE deliveries SET state='in_flight', claimed_by=$w,
       claim_expires_at=now()+interval '90 seconds'
WHERE delivery_id IN (
  SELECT delivery_id FROM deliveries
  WHERE state='pending' AND next_attempt_at <= now()
  ORDER BY next_attempt_at LIMIT 100
  FOR UPDATE SKIP LOCKED)
RETURNING *;
```
Lease expiry (worker died mid-send) is swept back to `pending`. Yes, this can double-send an event whose response was lost — that is the at-least-once contract; receiver dedup absorbs it.

## 4. Retry state machine

```
            ┌────────────────────── lease expired ──────────────┐
            ▼                                                    │
 pending ──claim──► in_flight ──POST──► classify response ───────┤
   ▲                                        │
   │  retryable (backoff, attempt++          ├─ 2xx ────────────► succeeded (terminal)
   └── next_attempt_at = now+delay) ◄───────┤
                                             ├─ non-retryable 4xx ► dead (terminal, DLQ)
                                             └─ attempts/age exhausted ► dead (terminal, DLQ)
```

**Response classification (the part everyone gets wrong):**

| Outcome | Class | Action |
|---|---|---|
| 2xx | success | terminal `succeeded` |
| 429 | retryable | honor `Retry-After` if present (clamped to [backoff_min, cap]); it overrides computed backoff |
| 408, 5xx, connect/read timeout, TLS/DNS error | retryable | backoff; **timeout after the request was written is an *unknown* outcome, not a failure** — must retry, dup is possible, dedup covers it |
| 3xx | failure | do **not** follow redirects (SSRF + signature confusion); retryable a few times, then dead |
| 400, 401, 403, 413, 422 | non-retryable | fast dead-letter — retrying a deterministic rejection is pure waste |
| 404 | semi | retry briefly (deploys flap), then dead |
| 410 Gone | contract | auto-disable the subscription |

**Backoff:** `delay = random_uniform(0, min(cap, base · 2^attempt))` — **full jitter** (AWS style). Deterministic `base·2^n` synchronizes the whole backlog into thundering-herd waves against a recovering endpoint; jitter must span the *entire* interval, not ±10%. Suggested: base 15 s, cap 1 h, max ~18 attempts ≈ 72 h horizon (this number is a load-bearing constant — see §8-A). Add a delivery-level timeout budget: connect 3 s, total 15 s.

**Poison handling — distinguish two diseases:**
1. **Poison message** (this payload fails with 4xx/persistent 5xx while siblings to the same endpoint succeed): dead-letter *just it* after classification/exhaustion. `dead` rows keep full payload + attempt history; expose `replay(delivery_id)` (re-enqueues with the **same** `webhook_id`) and alert on DLQ depth.
2. **Dead endpoint** (everything to a subscription fails): per-subscription circuit breaker on `consecutive_failures` → `paused_until` with endpoint-level exponential probe. Critically, **pausing must freeze per-delivery attempt counters** (don't burn all 18 attempts of 5,000 messages against a known-down host, mass-DLQing them). After e.g. 5 days continuously open → disable subscription + notify the owner out-of-band.

## 5. Ordering guarantees

**Contract: per-`partition_key` eventual convergence, not per-delivery FIFO.** At-least-once + retries + parallel dispatch makes strict global ordering physically incompatible with availability: if event N is failing, strict FIFO means head-of-line blocking of everything behind it, and dead-lettering the head *silently reorders anyway*.

- Default mode: deliver unordered/parallel; every payload carries `(partition_key, seq)`; the receiver applies **compare-and-set**: `apply iff incoming.seq > stored.seq for that key`, else ack-and-discard. Stale arrivals are dropped, terminal state is correct.
- Optional `ordered_mode` per subscription: dispatcher serializes per `(subscription, partition_key)` (one in-flight per key, next not claimable until predecessor terminal). **Ordering must be sacrificed when:** (a) the head exhausts retries — you either DLQ it and let the key advance (order broken, availability kept) or freeze the key (order kept, key unavailable) — make this a per-subscription policy, never pretend you can have both; (b) manual DLQ replay, which by definition arrives after successors; (c) lease-expiry duplicates racing their own retry.
- Strongest practical pattern: **thin payloads** — webhook says "entity X changed, seq N", receiver fetches current state from your API. Fetch-latest is naturally convergent and makes ordering *and* most idempotency concerns evaporate.

## 6. Receiver-side recipe (what your docs must mandate)

```sql
BEGIN;
  INSERT INTO processed_webhooks(webhook_id) VALUES ($id);  -- unique PK violation ⇒ duplicate
  -- on conflict: ROLLBACK, return 200 immediately, DO NOT re-execute
  <apply side effect>;   -- same txn
COMMIT;                  -- then return 2xx
```
Verify signature and timestamp window *before* touching the table. Enqueue-then-ack (return 2xx after durable local enqueue, process async) is the recommended shape for slow effects — sender timeout while the receiver is still working is a classic duplicate factory.

## 7. Re-signing across retries (small but sharp)

Retries resend the **byte-identical original payload** (never re-serialize — key order/whitespace changes break the HMAC and any receiver-side body-hash dedup), but the `Webhook-Timestamp` and signature are **regenerated per attempt**. Receivers enforce a ±5 min timestamp window for replay protection; a cached day-old signature from attempt #1 is correctly rejected at attempt #9, which looks like a mystery 401 → wrongful dead-letter.

## 8. The three subtlest correctness pitfalls

**A. Dedup-window expiry vs late retries and manual replays.**
The receiver's `processed_webhooks` table gets pruned ("keep 24 h") for hygiene, but the sender's redelivery horizon is 72 h of backoff — *plus* a human hitting "replay" on a DLQ item two weeks later, *plus* clock skew in wall-clock pruning. Any redelivery landing after the row is pruned is indistinguishable from a first delivery → **the effect executes twice, exactly in the rare/late cases where nobody is watching**. Why it bites: the two retention constants live in two different organizations' codebases and drift independently; the system passes every test because duplicates within minutes are always caught. Invariant to enforce and document: `receiver_dedup_retention > sender_max_backoff_horizon + max_replay_window`, replays keep the original `webhook_id` by construction, and for effects that matter, prefer *semantic* idempotency (the §5 seq compare-and-set, or "set state to X" rather than "increment") which has no window at all.

**B. Non-atomic dedup at the receiver (check-then-act, and mark-before-effect).**
Two mirrored failure modes: (1) `if not seen(id): apply(); mark(id)` — the ambiguous-timeout case guarantees concurrent duplicates exist (sender lease expires while the slow original is still in flight; both arrive within milliseconds), both pass the read check, **double effect** — a TOCTOU race no TTL tuning fixes; (2) the "fixed" version `mark(id); apply()` (or Redis `SETNX` before processing) crashes between mark and apply — the retry is now swallowed as a "duplicate", **zero effect**, silently violating at-least-once at the effect level. Why it bites: both versions are 100% correct single-threaded and under happy-path load; only crash + concurrent-retry interleavings expose them, and the second bug produces *missing* data, the hardest kind to notice. Only fix: dedup insert and side effect in **one ACID transaction**, with the *unique constraint*, not a prior read, as the arbiter. For inherently non-transactional effects (send an email), you cannot get exactly-once — choose which failure mode you prefer and add reconciliation; be honest about it in the contract.

**C. Per-message idempotency ≠ cross-message correctness (retry-induced stale overwrite).**
Event v1 for entity E fails (endpoint blip) → scheduled +40 min. Event v2 for E succeeds now. v1's retry later succeeds and the receiver — dutifully idempotent per `webhook_id`, seeing v1 for the first time — applies it, **overwriting v2 with stale state**. Every individual delivery satisfied "exactly-once effect"; the aggregate state is still corrupt, because retries are a *reordering machine* and per-message dedup says nothing about inter-message order. Why it bites: it emerges precisely and only when retries occur, i.e., during incidents, and it masquerades as "customer data mysteriously reverted." Fix is §5: monotonic `seq` per `partition_key` with receiver compare-and-set (discard `seq ≤ stored`), or thin payloads + fetch-latest. Corollary: `ordered_mode` + "DLQ the head and continue" quietly recreates this bug — a replayed head is a stale message by definition, so replays must also pass the seq gate.

*Runner-up worth knowing:* receivers that return 409 on duplicates (breaks the sender's outcome classifier — success mislabeled as terminal failure; §2), and re-serialized retry payloads breaking HMAC/dedup-by-body-hash (§7).
