# q9 — fable-raw (archetype: debugging-reasoning)

## Task

A web service's p99 latency spikes to 10x baseline, but ONLY at moderate load (not idle, not peak) and in bursts lasting ~200ms. p50 is unaffected. Enumerate every plausible root cause (stop-the-world GC, connection-pool exhaustion, lock/mutex contention, noisy-neighbor CPU steal, TCP retransmit/Nagle, thread-pool queueing, periodic cache stampede). Rank by fit to the EXACT signature (p99-only, moderate-load-only, ~200ms bursts, p50 fine) and for the top 3 give a definitive distinguishing test (a specific metric, trace, or experiment).

## Fable answer

# Diagnostic frame (what the signature constrains)

Before ranking, extract the hard constraints from the signature:

1. **p50 flat, p99 = 10x** → the affected fraction of requests is between ~1% and ~50%, realistically 1–5%. If bursts last 200ms and hit essentially all in-flight requests, burst frequency F satisfies 0.01 ≲ F × 0.2s → **bursts recur roughly every 0.5–20 seconds** during the bad regime. That cadence range itself is diagnostic (GC cycles, pool-eviction sweeps, cache TTLs, and CFS periods all live there; per-request random effects do not need it).
2. **Coherent ~200ms bursts** → favors a *global stall* mechanism (whole process/cgroup/flow frozen for 200ms) over per-request random slowness. If p99-baseline is ~20ms, then 10x ≈ 200ms ≈ the full burst width, i.e., affected requests wait out essentially the *entire* stall — consistent with a hard stop, not a partial slowdown.
3. **Moderate-load-only** is the strongest discriminator, because almost every queueing pathology is *monotonic* in load. Only three mechanism classes produce a mid-load maximum:
   - **Cold-resource churn**: a resource (pooled connection, thread, warm cache entry, TCP cwnd, TLS session, JIT state) decays during idle gaps. At idle there's almost no traffic to observe the cost (and few coincident victims); at peak the resource never goes cold; at moderate load the inter-arrival gap ≈ the idle/eviction timeout, so you churn constantly. This is a *resonance* between arrival gaps and decay timers.
   - **Regime change at peak**: the mechanism exists at peak but is masked or replaced — autoscaling adds capacity at peak; TCP switches from RTO to fast-retransmit when there's enough traffic to generate dup-ACKs; GC pauses become so frequent at peak that they lift p50 (a *different* signature that nobody filed).
   - **Threshold-crossing**: a trigger (allocation rate, burst parallelism over CPU quota) only crossed once load is non-trivial, combined with one of the above to explain "not at peak."
4. **Also note the magic numbers**: 200ms is *literally* Linux `TCP_RTO_MIN`; the max delayed-ACK timer on several stacks (Windows default 200ms); 2× the CFS period (100ms); a textbook mixed/major GC pause; and a typical TCP+TLS+DB-auth handshake.

**One structural caveat**: a purely load-*independent* 200ms stall (true noisy neighbor, cron job) hits a constant *fraction* of requests at every load level (fraction ≈ stall duty cycle, independent of RPS), so it cannot produce moderate-only p99 spikes by itself — it needs an amplifier (autoscaling at peak, or sub-p99 duty cycle at idle due to sample scarcity in short percentile windows). This demotes several intuitive candidates.

# Ranking (fit to the exact signature)

1. **Stop-the-world GC** — best fit to "coherent ~200ms bursts, p99-only"; moderate-only is explainable (idle = no allocation pressure; peak = scale-out or regime change) but is the one assumption you must verify.
2. **Connection-pool cold churn** (incl. keep-alive/TLS variants) — best fit to "moderate-load-only" (the resonance is *mechanically* mid-load-maximal); 200ms ≈ handshake; bursts slightly less coherent unless evictions batch.
3. **CFS quota throttling** — coherent quantized stalls, cheap to check, and note it *compounds* with #1: GC worker threads bursting all cores is the most common way a request-serving pod exceeds quota. Finding both is common.
4. **TCP tail-loss RTO** — the eeriest match to the literal 200ms; moderate-only mechanism (RTO vs fast-retransmit regime) is real but requires a lossy hop.
5. Thread-pool cold-start queueing. 6. Cache stampede (sliding-TTL variant). 7. Nagle/delayed-ACK. 8. Lock contention (only via periodic-holder variant). 9. Pure CPU steal (only via time-of-day confound).

# Definitive distinguishing tests — top 3

### 1. STW GC — the "descending-ramp" fingerprint + forced-GC injection
- **Metric/trace**: Enable pause logging (`-Xlog:gc*,safepoint` on JVM; `GODEBUG=gctrace=1` or `/gc/pauses` runtime metric in Go; `%GC` ETW events in .NET). Cross-correlate pause timestamps with per-request slow samples: **every** slow cluster must sit inside a logged pause window, and pause width must ≈ excess latency. On JVM, check *safepoint* logs too — time-to-safepoint stalls and non-GC safepoints (deopt, biased-lock revocation) mimic GC and are missed by GC-only logs.
- **The definitive fingerprint**: within one burst, plot each request's *arrival time* vs its latency. A global STW produces a **linear ramp with slope −1** (a request arriving t ms into a 200ms pause waits 200−t ms), all requests ending at the same wall-clock instant, **uniformly across all endpoints**. No per-resource cause (pool, lock, one lossy flow) produces endpoint-uniform victimization with a −1 ramp.
- **Experiment**: at moderate load in staging, inject `jcmd <pid> GC.run` (or `runtime.GC()`): if the injected pause reproduces the identical burst shape, and setting a pause-time-bounded collector (or bigger young gen) makes production spikes vanish, confirmed. **Falsifier**: any slow burst with zero logged pause/safepoint in the window kills this hypothesis.
- **Disambiguation from #3**: a CFS throttle also freezes the whole process and yields the same ramp — so *always* check `cpu.stat` in the same window (below) before declaring GC guilty; a 200ms "GC pause" is frequently 20ms of GC + 180ms of throttle *caused by* GC threads.

### 2. Connection-pool cold churn — pool-wait attribution + eviction-timer experiment
- **Metric/trace**: instrument (a) pool acquisition wait time and (b) connection-creation events (HikariCP `connectionCreation`/`connectionAcquire` timers, Go `sql.DBStats.WaitDuration` + `MaxIdleClosed`/`MaxIdleTimeClosed` deltas, envoy/nginx upstream `connect_time`). The confirming pattern: every slow request's excess latency is accounted for by acquire-wait or connect+TLS time; slow requests are **confined to one downstream dependency** (not endpoint-uniform — the anti-GC signature); the excess-latency histogram is **bimodal** with a mode exactly at your measured TCP+TLS+auth handshake time; and `MaxIdleTimeClosed`-style eviction counters tick at moderate load but are ~0 at peak.
- **Experiment (definitive, 1-line config)**: set `minimumIdle = maximumPoolSize` (or idle-timeout ≫ worst inter-arrival gap; for the HTTP variant, raise LB/upstream keep-alive idle timeout above client-side gaps). If moderate-load spikes disappear while peak/idle behavior is unchanged, confirmed. **Corroboration**: compute the inter-arrival-gap distribution per connection at moderate load — it should straddle the eviction timeout (the resonance condition). **Falsifier**: slow requests whose entire latency is inside application code with a warm connection already checked out.

### 3. CFS throttling — `cpu.stat` deltas + quota-removal A/B
- **Metric/trace**: read the cgroup's `cpu.stat` (`nr_throttled`, `throttled_usec`) or Prometheus `container_cpu_cfs_throttled_periods_total` at 1s resolution. Confirming pattern: `throttled_usec` increments **exactly and only** during burst windows, and per-burst throttled time ≈ burst width; stall widths cluster at **multiples of (period − allotted runtime)**, i.e., quantized near n×100ms — the quantization is the fingerprint no other cause shares. Distinguish from *steal*: `%steal` in `/proc/stat` / hypervisor `CPU steal` metric flat ⇒ it's your quota, not a neighbor.
- **Experiment (definitive)**: in one canary pod, remove the CPU limit (`cpu.max = max`) or double the quota, keep requests/limits elsewhere identical, and A/B p99 at moderate load. Spikes vanish in the canary only ⇒ confirmed. Then check *why* moderate-only: pull HPA replica counts vs load — if replicas scale at peak so per-pod CPU stays under quota, the "not at peak" mystery is closed. **Falsifier**: `nr_throttled` delta = 0 across a captured burst.

**Recommended order of execution**: capture one burst with all three instruments simultaneously (GC/safepoint log + request-arrival-vs-latency scatter + `cpu.stat` 1s deltas + pool metrics). The victim pattern alone usually decides it in one incident: **endpoint-uniform with −1 ramp** → GC or throttle (split on `cpu.stat`); **single-dependency, bimodal at handshake time** → pool churn; **constant 200.x ms excess on network-heavy calls only** → go straight to `ss -ti`/`nstat TcpRetransSegs` and a pcap for the #4 RTO hypothesis.
