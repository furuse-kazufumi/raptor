# q8 — fable-raw (archetype: hard-analysis)

## Task

Compare consistent hashing (ring + virtual nodes) vs rendezvous / highest-random-weight (HRW) hashing for a distributed cache. For each: the fraction of keys remapped when a node is added or removed, the load-balance variance (and how virtual nodes / HRW affect it), and the per-lookup cost. State precisely where each wins, and identify the single most common misconception about consistent hashing's remapping guarantee and correct it.

## Fable answer

## Consistent Hashing (ring + virtual nodes) vs Rendezvous/HRW for a Distributed Cache

Setup: `K` keys, `N` nodes, `v` virtual nodes (tokens) per physical node for the ring.

---

### 1. Fraction of keys remapped on membership change

**Both schemes have the same *expected* minimal disruption.** This is the headline fact people get wrong (see §5).

**Add one node (N → N+1):**
- **Ring:** the new node's tokens capture arcs; expected total captured fraction = `1/(N+1)`. Without vnodes the *actual* fraction is one arc length — a random variable, roughly `Exp(N)`-distributed (Beta(1, N)), with coefficient of variation ≈ 1. You may move 3× the expectation or almost nothing. With `v` vnodes the captured mass is a sum of `v` sub-arcs, concentrating toward `1/(N+1)` with relative stddev ≈ `1/√v`.
- **HRW:** each key independently moves iff the new node's score `h(key, node_new)` beats all `N` existing scores — probability exactly `1/(N+1)` i.i.d. per key. Moved count ~ `Binomial(K, 1/(N+1))`, i.e. extremely tightly concentrated (relative stddev ≈ `√(N/K)`, negligible for cache-sized K).
- In both schemes, displaced keys move **only onto the new node** — no third-party shuffling.

**Remove one node:**
- Both: exactly the departed node's keys move — fraction = that node's current share, expectation `1/N`. The critical difference is the **destination distribution**:
  - Ring, no vnodes: *all* of the dead node's keys land on its single clockwise successor → that node's load roughly doubles → cascading-failure risk in a cache fleet.
  - Ring, `v` vnodes: keys scatter to the ~`v` distinct successors of its tokens — good, but destinations are the specific token-neighbors, and with replication you must dedupe same-physical-node successors.
  - HRW: each orphaned key goes to its per-key *runner-up* node, which is uniform over all `N−1` survivors. Failure load spreads perfectly with zero configuration. **This is HRW's cleanest practical advantage and is frequently overlooked.**

Edge case: **simultaneous/concurrent changes.** Ring: keys still only move along affected arcs; total movement ≈ sum of individual expectations. HRW: same, and a key never moves unless one of the changed nodes is (or becomes) its argmax — no transitive churn in either scheme.

---

### 2. Load-balance variance

- **Ring, 1 token/node:** arc lengths are jointly Dirichlet(1,…,1); each node's share has mean `1/N`, CV ≈ 1 (i.e., stddev ≈ the mean itself — terrible). The largest arc is ≈ `ln N / N`, so the hottest node carries ~`ln N ×` the average with high probability. Unusable bare for a cache.
- **Ring, v vnodes:** a node's share is the sum of `v` near-independent arcs → CV ≈ `1/√v`. Rule of thumb: `v ≈ 100` → ~10% stddev; `v ≈ 400–1000` → ~3–5% (hence Cassandra's 256, Riak's 64–256). Costs: `O(N·v)` memory, `O(v log(Nv))` work per membership change, gossip/metadata bloat, and replica-placement/repair complexity. Balance improves only as `√v` — diminishing returns.
- **HRW:** each key is an independent uniform draw over nodes (the argmax of N i.i.d. hashes is uniform), so per-node load ~ `Binomial(K, 1/N)`: CV ≈ `√(N/K)`. With K = 10⁷ keys, N = 100: CV ≈ 0.3%. HRW is effectively the `v → ∞` limit of vnodes, with zero tuning and zero extra state.
- **Neither fixes popularity skew:** a single hot key overloads one node identically in both. That needs client-side caching, key salting/replication of hot keys, or bounded-load techniques.
- **Weighted nodes:** HRW handles heterogeneous capacity cleanly and exactly via the logarithmic method (`score_i = −w_i / ln(u_i)` where `u_i = h(key,i)` normalized to (0,1)). The ring approximates weights coarsely by vnode count (integer granularity, more tokens = more state).
- Nuance: if strict balance under a ring is required, **consistent hashing with bounded loads** (Mirrokni–Thorup–Zadimoghaddam; used by Vimeo/Google) caps any node at `(1+ε)×` mean at the cost of occasional forwarding — that's the principled fix, not "more vnodes."

---

### 3. Per-lookup cost

- **Ring:** 1 key hash + binary search over `N·v` sorted tokens: `O(log(Nv))` comparisons. For N=1000, v=256 → 256k tokens ≈ 18 probes, but these are pointer-chasing/cache-missing probes over a multi-MB array. Memory `O(Nv)`. Membership change: `O(v log(Nv))`.
- **HRW:** `N` fast hash evaluations (combine a precomputed per-node digest with the key hash; a few ns each with xxHash/murmur-style mixing), take the argmax: `O(N)` time, `O(N)` state (just the node list), `O(1)` membership change. For top-R replica selection, partial-select top R.
- **Crossover:** despite asymptotics, HRW's linear scan over a contiguous array is often *faster in wall clock* than the ring's binary search up to N ≈ 100–1000. Beyond that the ring wins per-lookup. An `O(log N)` hierarchical/skeleton HRW exists but sacrifices simplicity and slightly degrades disruption behavior at group boundaries — rarely worth it.

---

### 4. Where each wins (precisely)

**HRW wins when:**
- N is small-to-moderate (≲ few hundred) — typical memcached/Redis client-side sharding;
- you want near-perfect key balance with no tuning and `O(N)` state;
- graceful failure redistribution matters (runner-up property spreads a dead node's load over all survivors);
- heterogeneous node weights are needed exactly;
- replica selection: top-R scores give a clean, uniform, coordination-free replica set;
- multiple independent clients must agree on placement with nothing but the node list.

**Ring + vnodes wins when:**
- N (or N·v effective) is large and lookup rate is extreme, so `O(log)` vs `O(N)` per lookup actually dominates;
- you need **contiguous range ownership** — token ranges enable range scans, efficient bulk streaming/anti-entropy repair on membership change, and partition-transfer bookkeeping (the real reason Dynamo/Cassandra/Riak use rings: you can hand off "arc (a, b]" as a unit rather than enumerate keys). HRW has no notion of a transferable range — recomputing ownership of existing on-disk data requires evaluating every key;
- membership is very dynamic and you want incremental `O(v log Nv)` structural updates with a stable, inspectable ownership map.

For a pure **distributed cache** (no range transfer needed — misses just refill), HRW is usually the better default; the ring earns its complexity in storage systems, not caches.

---

### 5. The single most common misconception about the remapping guarantee — corrected

**Misconception:** "Consistent hashing guarantees that *exactly* K/N keys are remapped when a node is added or removed — and this minimal-disruption property is what makes it unique."

**Correction, both halves:**
1. The `K/N` figure is an **expectation over hash randomness, not a bound**. On a bare ring (few/no vnodes), the remapped fraction is the captured/lost arc mass — a random variable with CV ≈ 1; the largest arc is ~`ln N / N`, so a single membership change can remap ~`ln N ×` more keys than "guaranteed" (≈ 7× at N=1000). Only virtual nodes (concentration ~`1/√v`) — or HRW, whose per-key independence gives binomial concentration essentially for free — make the realized fraction reliably close to `1/N`.
2. Minimal disruption is **not unique to the ring**: rendezvous hashing has exactly the same property (expected `1/(N+1)` moved on add, only to/from the affected node), and it predates most deployments' awareness of it (Thaler & Ravishankar 1996 vs Karger et al. 1997). Choosing ring-based consistent hashing "for the remapping guarantee" is therefore not a differentiator; the actual trade is `O(log Nv)` lookups + range ownership (ring) versus perfect statistical balance + `O(1)` state + uniform failure spreading at `O(N)` lookup (HRW).
