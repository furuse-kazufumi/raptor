# q4 — fable-raw (archetype: debugging-reasoning)

## Task

A service intermittently returns stale data: about 1 request in 10,000 reads a value that was overwritten seconds earlier. The stack is: clients -> load balancer -> N stateless app servers -> a Redis cache (read-through) -> Postgres primary with one async read-replica. Enumerate ALL plausible root causes for the stale reads, rank them by likelihood given the '1 in 10,000, seconds-stale' signature, and for the top 3 give a DEFINITIVE test that distinguishes that cause from the others (an experiment or a specific log/metric to check). Be precise about why the signature points where it does.

## Fable answer

# Stale-Read Root-Cause Analysis: clients → LB → app servers → Redis (read-through) → Postgres primary + async replica

## 0. First, decode the signature

Two numbers carry almost all the diagnostic information:

**"1 in 10,000" (P ≈ 10⁻⁴)** — this is a *coincidence rate*, i.e. the product of two modest probabilities, or a small per-operation failure rate. It is:
- Too **low** to be a misconfigured server (1 bad server out of N gives P ≈ 1/N ≈ 10⁻¹–10⁻²), a systematically wrong read path, or "TTL-only, no invalidation" design (that scales with write rate and would be far noisier on hot keys).
- Too **high and too steady** to be failover/split-brain events (those are bursty: zero for weeks, then thousands of stale reads in one minute).
- Exactly right for `P(cache miss) × P(key was written within window W before the miss)`. Example: 2% miss rate × (1s window / 60s mean inter-write interval on read keys) ≈ 3×10⁻⁴.

**"Seconds stale"** — the staleness magnitude names the mechanism's clock:
- **Seconds** is the natural timescale of: Postgres **async replica lag** under load, **short cache TTLs**, **async invalidation pipelines** (pub/sub, CDC, queues), leaked-transaction MVCC snapshots, and tail GC/network pauses widening race windows.
- It is *not* the natural timescale of: healthy intra-DC Redis replication (sub-ms–ms), DNS TTLs (minutes), long cache TTLs (minutes–hours), or crash-recovery data loss (permanent).

**One subtlety that matters for the whole analysis (amplification):** in a read-through architecture, any mechanism that gets a stale value *into* Redis converts one rare poisoning event into `read_rate_on_key × min(TTL, time-to-next-invalidation)` stale reads. So the observed 10⁻⁴ read-level rate may be produced by a poisoning-event rate that is 10–1000× rarer. When ranking causes, think in terms of *poisoning events*, not stale reads.

Also verify the observation itself before debugging: "overwritten seconds earlier" is usually established by comparing a write log timestamp against a read log timestamp — **clock skew between hosts can manufacture phantom staleness**. Cheap check: a canary key written with a monotonic counter every second by one writer, read continuously, with both operations logged through the same clock. If the canary never shows staleness, keep it running — it becomes your detector for every experiment below.

## 1. Full enumeration of plausible root causes

### Tier A — strong signature fit (both rate and timescale match)

**A1. Cache-miss repopulation sourced from the async replica.**
On a miss, the read-through loader's SELECT lands on the replica (deliberately "for read scaling," or accidentally via pgbouncer/HAProxy/RDS-proxy pool mixing, a DNS name that round-robins primary+replica, a reader-endpoint DSN in the cache-fill code path, or a subset of pooled connections pinned to the replica). Writes go to the primary and invalidate Redis; a miss within the lag window re-caches the pre-write value.
*Fit:* staleness = replica lag = seconds, exactly. Rate = miss% × P(recent write) ≈ 10⁻⁴. **Best single fit.**

**A2. Cache-aside / read-through repopulation race ("stale SET after invalidate").**
Classic interleaving: reader misses → reads DB (old value) → is delayed (GC pause, network hiccup, slow event loop) → meanwhile writer commits new value and DELETEs the key → delayed reader SETs the *old* value. The poisoned entry then serves stale reads for seconds (until TTL or the next write).
*Fit:* poisoning rate = miss% × (DB-fetch latency / inter-write interval) ≈ 10⁻⁵–10⁻⁶, amplified by reads-per-key-per-TTL back up to ~10⁻⁴. "Seconds stale" = short TTL or next invalidation. Includes the single-flight/dogpile-lock variant (a fetch that *started* before the write commits *after* the invalidation) and the write-side ordering variant (invalidate-then-write-DB, reader repopulates in between).

**A3. Failed, dropped, or asynchronous cache invalidation.**
The DELETE after a write is fire-and-forget and occasionally times out / errors / is swallowed by an exception handler; or invalidation rides an async channel (Redis pub/sub — which is at-most-once, keyspace notifications, CDC/Debezium, a queue) that delays or loses messages. Stale value survives until TTL.
*Fit:* rate = per-write invalidation-failure rate (10⁻³–10⁻⁵ is typical for timeouts under load) × read amplification; "seconds" fits if TTL is short or the async channel's delay is seconds.

### Tier B — plausible, fits one axis well, check after Tier A

**B1. Stale MVCC snapshot on a pooled Postgres connection.** A connection returned to the pool while *idle in transaction* (leaked ORM session, missing commit/rollback on an error path, `REPEATABLE READ` default) — the next borrower reads a snapshot taken seconds ago. Rate = fraction of requests that draw the poisoned connection; staleness = age of the leaked transaction. Detectable via `pg_stat_activity` (`state = 'idle in transaction'`, old `xact_start`).

**B2. Hidden in-process cache on the "stateless" app servers.** An ORM second-level cache, `lru_cache`/caffeine/Guava memoizer with a seconds-TTL, a request-scoped cache leaking across requests, or a module-level variable. Server A serves its local copy after server B wrote. "Seconds stale" matches a seconds TTL exactly; rate = P(local hit on a recently-overwritten key).

**B3. Redis-side topology staleness.** Reading from Redis replicas (`READONLY` in cluster mode, replica reads enabled in the client), Sentinel failover with lost acked writes, or two app servers holding *different shard maps* during a config rollout (write/invalidate goes to shard A, read hits shard B's old copy). Healthy intra-DC Redis lag is ms not seconds (weakens the fit), and failover/rollout causes are bursty rather than steady 10⁻⁴ — rank below Tier A unless you run cross-region Redis replication (ElastiCache Global Datastore etc.), which *does* have seconds of lag and would jump to Tier A.

**B4. HTTP-layer caching above the app servers.** LB/CDN/proxy or client honoring a leaked `Cache-Control: max-age=…`/ETag on a few endpoints, caching GETs for seconds. Rate = fraction of traffic hitting a warm proxy entry. Trivially checkable: stale responses that never appear in app-server access logs.

### Tier C — possible but signature-mismatched; rule out cheaply

- **C1. Delayed duplicate write replay** (queue retry / at-least-once consumer / LB retry of a non-idempotent POST re-applies the *old* value after the new one). Distinguishing fingerprint: the *database itself* holds the old value afterward — it's not a stale read, it's a real regression of state.
- **C2. Last-write-wins with clock skew** dropping the newer write (only if the write path uses timestamps for conflict resolution — unusual in this stack; same DB-holds-old-value fingerprint as C1).
- **C3. Write-behind / async DB persistence**: cache updated, DB write deferred; a concurrent miss reads the not-yet-written DB. Only if such a component exists.
- **C4. One misconfigured app server** (wrong Redis endpoint, replica DSN for all reads). Rate would be ~1/N ≈ 10⁻¹–10⁻², 2–3 orders too high — ruled out *as a sole cause*, but "one server × only cache-miss paths" can land at 10⁻⁴, so keep it as a sub-hypothesis of A1 (check per-server stale-rate skew).
- **C5. Redis eviction pressure (`maxmemory`)** — not a root cause itself, but raises miss rate and therefore multiplies A1/A2.
- **C6. Monitoring artifact / clock skew in logs** — see §0; rule out first, it costs an hour.

## 2. Ranking (most → least likely for *this* signature)

| Rank | Cause | Why the signature points here |
|---|---|---|
| 1 | **A1** replica-sourced cache fill | Only cause where "seconds" is *mechanically guaranteed* (= replica lag) rather than coincidental; rate arithmetic lands on 10⁻⁴ with unremarkable miss/write rates; extremely common misconfiguration (reader endpoints, pool mixing). |
| 2 | **A2** invalidate/repopulate race | Textbook cache-aside defect; produces exactly "rare + bounded-duration" staleness; needs no misconfiguration at all — it's latent in most delete-on-write implementations and surfaces at 10⁻⁴–10⁻⁶ under load. |
| 3 | **A3** failed/async invalidation | Common (fire-and-forget deletes, pub/sub is lossy by design); fits if TTL or propagation delay is seconds; slightly behind A2 because it requires an actual failure/loss, whereas A2 needs only scheduling luck. |
| 4 | B2 in-process cache | Perfect "seconds" fit, but requires a component that contradicts the stated architecture — likelihood hinges on code audit. |
| 5 | B1 leaked-transaction snapshot | Right timescale, right rarity; less common than cache bugs and usually accompanied by other symptoms (pool exhaustion, bloat). |
| 6 | B3 Redis topology | Wrong timescale intra-DC (ms) or wrong temporal pattern (bursty); promote if cross-region. |
| 7 | B4 HTTP caching | Easy to check, moderately common, but read-through Redis is the stated design center of gravity. |
| 8 | C1/C2 write replay / LWW | Different fingerprint (DB is actually stale) — check the DB value once and this branch dies or dominates. |
| 9 | C4 single bad server (sole cause) | Rate 2–3 orders too high alone. |
| 10 | C3/C5/C6 | Conditional/multiplier/artifact. |

**Three cheap observables split almost the entire space — instrument these first:**
1. **Cache status of each stale response** (tag responses hit/miss-fill): stale-on-*fill* → A1/A2 origin; stale-on-*hit* → a previously poisoned entry (A1/A2 amplified) or A3/B2.
2. **Correlation of stale-event rate with `pg` replica lag**: correlated → A1; flat → A2/A3/B*.
3. **Same-key clustering**: stale reads for one key repeating until a TTL boundary → poisoned-cache family (A1/A2/A3); isolated single stale reads scattered across keys → B1/B4/snapshot-style causes.

## 3. Definitive tests for the top 3

### Test 1 — A1 (cache fill reads the replica)

**Dose–response experiment (the smoking gun):** in a canary/staging environment — or briefly in production during low traffic — run `SELECT pg_wal_replay_pause();` on the replica for 60 s, then `pg_wal_replay_resume();`. If A1 is the cause, the stale-read rate **rises during the pause and the measured staleness grows linearly to ~60 s**, tracking the induced lag exactly. No other cause on the list responds to replica replay state: A2's race window is set by app fetch latency, A3's by TTL/invalidation delivery — both are indifferent to the replica.
**Non-invasive confirmations:** (a) on the replica, enable `log_statement`/`pg_stat_statements` and look for the cache-fill SELECTs — *any* occurrence on the replica of a query that should feed Redis is proof of the routing defect; also `pg_stat_activity` on the replica for app-server client addresses. (b) Plot stale-event count vs. `now() - pg_last_xact_replay_timestamp()` (or `pg_stat_replication.replay_lag` on the primary) — A1 predicts stale events concentrate in high-lag minutes and per-event staleness ≤ concurrent lag.
**Fix-confirms:** point the cache-fill DSN at the primary for 24 h; A1 predicts stale reads drop to ~zero, and per-server breakdown identifies a C4 variant (one server's rate ≫ others).

### Test 2 — A2 (invalidate/repopulate race)

**Instrumentation fingerprint:** embed a monotonic version (`updated_at` or a version column) inside every cached value, and log every cache `SET k` with `(version, t_db_read_start, t_set)` and every `DEL k` with timestamp. A2 has a unique, unambiguous log signature: **a `SET(k, version=v_old)` whose `t_db_read_start` precedes a `DEL(k)` for the same key, with `t_set` after it.** Neither A1 (the SET carries a *replica-stale* version but with no interleaved DEL between read-start and set) nor A3 (no SET involved at all — the DEL simply never landed) produces this interleaving. With versions in the cache you can also audit live: sample keys and compare Redis version vs. primary version.
**Amplification experiment (dose–response):** in a canary, inject an artificial 200 ms sleep between the DB fetch and the cache SET in the read-through loader. A2 predicts the stale rate on that canary rises by roughly `200ms / normal_fetch_latency` (1–2 orders of magnitude); A1 and A3 predict no change. Conversely, deploying a compare-and-swap SET (Lua: set only if embedded version is newer than the resident one) or a post-invalidation tombstone window should drive the rate to zero *only* if A2 is the cause.

### Test 3 — A3 (failed / async invalidation)

**Write-side verification probe:** after every DB write, schedule an async check at +100 ms and +2 s that reads the Redis key and asserts it is either absent or carries the new version, logging violations *with the causal classification*:
- key **never deleted** (no DEL logged / DEL returned error or timed out) → **A3 confirmed**, and the client-side DEL error counter (plus Redis `SLOWLOG` and timeout metrics at the same instants) tells you which failure mode;
- key **was deleted, then reappeared with the old version** → that is A2, not A3 (the probe cleanly separates the two, which naive "cache is stale" checks cannot);
- key holds an old version **and the DEL succeeded and nothing re-set it** per logs → look upstream (async invalidation channel). For pub/sub–based invalidation, compare published vs. received invalidation counts per app server — Redis pub/sub is at-most-once, so any gap under connection churn is the answer; the stale-read rate will correlate with subscriber reconnect events.
**Static tell:** grep the write path for fire-and-forget deletes (no await/no error handling). If invalidation delay rather than loss is suspected, measure publish→delivery latency with a heartbeat invalidation message; A3-by-delay predicts staleness duration ≈ that latency distribution.

## 4. Suggested execution order

1. Rule out C6 (clock-skew artifact) with the monotonic canary key — 1 hour, and the canary then powers every later test.
2. Check the DB value at incident time once — instantly kills or crowns C1/C2.
3. Add the three cheap observables (§2) — they usually pick the tier before any experiment runs.
4. Run Test 1 (replay-pause) — cheapest definitive experiment, targets the most likely cause.
5. If negative, ship the version-in-value instrumentation (Test 2's fingerprint + Test 3's probe share it) — one deployment definitively separates A2 from A3.
6. Whatever the root cause, note the durable mitigations that close *several* branches at once: versioned CAS on cache SET, short TTL as a staleness ceiling, invalidation with retry + error metrics, and cache fills pinned to the primary (or gated on `replay_lsn ≥ write LSN`).
