# オーケストレーションで Opus を「上位モデル」級にできるか、正直に測ってみた

> 上位モデルがもうすぐ使えなくなる。だから「並列に何度も考えさせて検証する」足場（scaffold）で、
> 手元の Opus を上位モデル級に引き上げられないか——を、**盛らずに測った**記録です。
> 結論から言うと「タスク次第。一律には届かない。そして一番の収穫は別のところにあった」。

---

## 0. この記事は何の記録か（先に結論）

- **やったこと**: Claude Opus を、1 回の深い推論ではなく **オーケストレーション**（分解 → 並列に多様な試行 → 敵対的に検証 → 統合）で走らせ、上位モデル（Fable）の 1 パス品質を「買い戻す」足場を作り、**本当に届くのかを独立の判定者で測った**。
- **正直な結果**:
  1. **客観的に正解が決まる推論タスクでは、Opus は既に天井**だった（上位モデルと差が出ない）。足場は無力どころか、あるタスクでは**自分でバグって減点**した。
  2. **オープンな品質タスク**（設計・仕様・分析）では初めて構造が出た。**素の Opus 単発は一度も 1 位にならず**、上位モデルは「設計」で強く「分析」で弱く、足場は「分析」で勝ち「設計」で**素の Opus より劣化**した。
  3. 一番効いたのは品質の底上げではなく、**別系列モデルによる検証**（相関した盲点を突く）だった。
- **教訓**: 「異常に良い結果は内訳を疑う」を自分の実験に適用したら、`一律 parity 達成` という美味しい主張は**成立しなかった**。代わりに「どのタスクに足場を当てるべきか」という実用的な地図が残った。

---

## 1. 用語（先に短く。詳細は本文で）

| 用語 | 短い説明 |
|---|---|
| **オーケストレーション (orchestration)** | 1 つの LLM 呼び出しでなく、複数のサブエージェントを分解・並列・検証・統合して協調させること |
| **テスト時計算 (test-time compute)** | 学習済みモデルに対し、推論時に計算を「足す」ことで品質を上げる考え方（今回は並列試行＋検証） |
| **生成と検証のギャップ (generation–verification gap)** | 「答えを作る」より「答えを確かめる/選ぶ」方が安いときに、足場が効くという原理。逆に検証が生成と同じだけ難しいと足場は無力 |
| **天井効果 (ceiling effect)** | ベースラインが既に満点で、改善余地が測れない状態 |
| **相関した盲点 (correlated blind spot)** | 同じ重みのモデル同士だと同じ間違いを共有し、多数決でも誤答が生き残る現象 |
| **perishable（消えもの）** | 上位モデルの出力そのもの。アクセスが切れたら二度と採れない |

---

## 2. 動機：上位モデルが消える前に

上位モデル（社内呼称 Fable、Opus より 1 段上のティア）は近くアクセスできなくなる。
一方で日々の作業は Opus に降りる。ならば **「Opus を足場で上位モデル級に引き上げる」** 仕組みが要る——
という発想で `fable-parity` という足場集を作った。6 つのワークフロー（深い推論・敵対的検証・
研究統合・計画批評・研究検証・計画検証）を、すべて **Workflow ツール** の上に載せた。

思想の核はひとつ。**上位モデルが 1 パスで勝つのは、主に「1 回の推論の深さ・自己修正・探索幅」による。
その差は Opus 側でオーケストレーションを"消費"すれば買い戻せる**——ただし
**生成と検証のギャップが有利なときだけ**。

ここまでは仮説。問題は「本当に買い戻せているか」を、**測っていなかった**こと。

---

## 3. 正直な負け その1：客観推論は「天井」だった

まず、答えが一意に決まる客観タスクで測った。**キーは手で書かず Python の総当りで計算**した
（著者の勘違いでベンチマークを汚さないため）。ナイト＆ネイブ、制約スケジューリング、
多バグ修正、DFA トレース、剰余演算……。

3 アーム（opus 単発 / 上位モデル単発 / opus+足場）で採点した結果:

> **3 アームすべて満点。opus 単発が既に全問正解。**

さらに難易度を上げて再挑戦した（60 手の状態機械、4 集合の包除原理、Wythoff ゲーム、
非線形漸化式の第 50 項、格子経路……）。結果:

> **opus 単発 9/9。累計 18/18。上位モデルとの差はゼロ。**

これは足場が弱いのではない。**ベースラインが完璧すぎて、差を測る土俵が無い**のだ。
足場の理論そのものが「モデルが既に解けるものを足場化するな（コストだけ増える）」と言っている。
その理論に、自分の実験がそのまま当たった。

**さらに正直な話**：この難タスク群で、足場（opus+deep-reason）が **1 問だけ落とした**。
中身を追うと、統合エージェントが `{answer:"test"}` という**スキーマは満たすが中身が空の
プレースホルダ**を出荷していた。つまり **オーケストレーションが、素の Opus が解けるタスクに
"失敗する余地"を足していた**。これは足場の弱点の生きた実例で、隠さず修正した
（統合結果が異常に短ければ検証済みの最良試行にフォールバックするガードを追加）。

---

## 4. 方向転換：効いたのは「別系列による検証」だった

天井で足場が無力なら、**足場のどこに価値があるのか**。ここで理論に立ち返る。
足場の生命線は「生成と検証のギャップ」だ。ところが——**検証者まで Opus だと、
生成者と同じ重みを共有し、同じ盲点を持つ**。自信のある誤答が多数決を勝ち抜く。
実際、上の "test" 事件は Opus の自己検証が素通しした結果だった。

そこで **検証だけを別のモデル系列に出した**。OpenAI Codex（gpt-5.4、非 Anthropic 系）を
「反証専門」で呼び、荷重のある主張を 1 つずつ潰させる小さな道具（`ext_verify`）を作り、
足場の検証段に配線した。

**そして実際に効いた瞬間が来た。** 計画検証（plan-verify）を FastAPI のレート制限計画に
かけたとき、ある前提——「あるライブラリは Redis ネイティブで worker 間共有が自動」——を
**Opus の検証者は "確認済み" と判定**した。ところが **別系列の Codex が具体的根拠で反証**した:
「そのライブラリの最新版は別実装に移行しており、その API も retry メタデータも存在しない」。
結果、その前提は "不確実" に格下げされ、**"着手前にコードを読んで Opus と Codex の食い違いを
解消せよ"** という検証ステップが計画に自動で織り込まれた。

これは **相関した盲点を、別系列が突いた**実例だ。Opus だけのパイプラインなら、
自信のある誤りをそのまま出荷していた。**同じモデルに自分の宿題を採点させない**——
この 1 点が、今回いちばん実測で価値が出た改善だった。

---

## 5. 初めて構造が出た：品質軸の測定

客観正解が天井なら、**上位モデルと Opus の差が出るとすれば「品質軸」**しかない——
深さ、網羅、微妙な正しさ。ここは正解キーが無いので、**独立した blind 判定者**が要る。

そこで、5 つのオープンな設計・仕様・分析タスク（マルチテナントのレート制限設計、
ISO-8601 duration の全域仕様、Fibonacci ヒープ vs pairing ヒープ、間欠的な stale read の
根本原因、ホットカウンタの並行戦略）で 3 アームの回答を採り、**Codex（非 Anthropic、
Opus とも上位モデルとも独立）に、モデル名を伏せた匿名 3 答を品質でランク付けさせた**
（位置バイアスを消す決定的シャッフル付き）。

結果（N=5、単一 blind 判定、指標的で統計的検出力はない）:

| 指標 | 値 |
|---|---|
| 1 位獲得 | 足場 **3/5**・上位モデル **2/5**・**素の Opus 0/5** |
| 足場 > 素の Opus | **4/5** |
| 上位モデル > 素の Opus | **3/5** |
| 足場 > 上位モデル | **3/5** |

**さらに 10 タスクを安く追試**した。再生成できないのは上位モデルの出力だけなので、
そこだけ凍結しておき、Opus 単発を後から足して **2 者 blind 比較**（上位モデル vs 素の Opus）
を回した。結果：**上位モデルが素の Opus に 7/10 勝利**。3 アーム分と合わせると
**計 15 タスクで上位モデルが素の Opus に 10/15 勝利**。しかも **Opus が勝った 5 本は
「証明・数値・デバッグ」など"微妙な技術点を正確に詰める"タスクに集中**していた。

だが**大事なのは合計でなくパターン**だ:

- **素の Opus 単発は 3 アームで一度も 1 位にならず、N=15 でも上位モデルに 10/15 で負けた**
  → 単発品質のギャップは**実在する**（客観軸では見えなかったもの）。ただし劣勢は一様でなく、
  Opus は「証明・数値・厳密デバッグ」系では上位モデルに勝ち返す。
- **上位モデルは「設計・仕様」で勝ち、「分析・デバッグ」で最下位** → 上位モデルは万能ではない。
  1 パスで広く整った回答を出すタスクで強く、微妙な技術的判別を要するタスクで崩れる。
- **足場は「検証が有利な分析タスク」で勝ち、「一貫性重視の設計タスク」で素の Opus すら下回った**
  → 統合・接ぎ木の段が、単一の深い 1 パスの一貫性を壊す。**足場はタダではなく、一様に良くもない。**

**正直な結論**：「Opus+足場は上位モデル品質に届くか」は **タスク依存**。
分析系では超え、設計系では上位モデルにも素の Opus にも劣る。**一律の parity 主張は成立しない。**
実用的な答えは「足場を分析タスクに routing し、一貫性重視の設計タスクには当てない」。

## 6. 方法論として残ったもの（ここが再利用可能な資産）

- **キーは計算で作る**：客観タスクの正解を手で書くと、著者の間違いがベンチを汚す。総当り/厳密計算で保証。
- **判定者は独立系列で、blind に**：自己採点は禁物。非 Anthropic の Codex に匿名ランクさせ、
  決定的シャッフルで位置バイアスを消す。
- **perishable ファースト**：3 アームのうち再生成できないのは上位モデルの出力だけ。だから
  **上位モデルの回答を安く大量に凍結**し（1 エージェント/タスク）、Opus 側と判定は後からでもよい。
  今回、品質 15 タスク分の上位モデル出力をディスクに凍結した。
- **異常に良い結果は内訳を疑う**：`一律 parity 達成` は美味しいが、**測っていないことは主張しない**。
  出たのは「タスク依存」という地味だが正しい地図だった。

## 7. 一枚でまとめると

| 軸 | 測定結果 | 足場の価値 |
|---|---|---|
| 客観的正解（キーあり） | Opus ≈ 上位モデル（**2 度天井、18/18**） | **無い**（むしろ自爆リスク） |
| オープンな品質（判定制） | 素の Opus は 3 アームで 0/5 勝、N=15 で上位モデルに 10/15 負け。上位モデルは設計で強く証明・数値で弱い | **タスク依存**（分析で勝ち、設計で劣化） |
| 検証の相関盲点 | Opus の "確認済み" を別系列が反証 | **ここが本命**（実測で唯一はっきり効いた） |

**盛れば「オーケストレーションで Opus を上位モデル級にした！」と書ける。
でも正直に測ると、そうは言えなかった。**代わりに手に入ったのは、
「どこで足場が効き、どこで別系列検証が効き、どこでは何もするな」という、
明日から使える運用の地図だった。研究の価値は、勝った気になることではなく、
**内訳を正直に開示すること**にある——という家訓を、自分の実験で確かめた回でした。

---

*付記：数値はすべて小 N・単一 blind 判定の指標値であり、統計的に検出力のあるベンチマークではありません。
「測った範囲でこう出た」以上のことは主張しません。上位モデルアクセスが消える前に凍結した
出力群を基準に、今後より大きな N で追試できるようにしてあります。*
