# オーケストレーションで Opus を「上位モデル」級にできるか、正直に測ってみた（実装と実例つき）

> 上位モデルがもうすぐ使えなくなる。だから「並列に何度も考えさせて検証する」足場（scaffold）で、
> 手元の Opus を上位モデル級に引き上げられないか——を、**実装して・実例で・盛らずに測った**記録です。
> 結論：「一律に届く」とは言えなかった。でも **明日から使える道具と運用地図**は残った。

この記事は「やってみた自慢」ではなく、**あなたが同じことを再現できる**ように、
仕組み・コード・実際の入出力・失敗例まで出します。長いです（Qiita 長文）。

---

## 1. 3 行のまとめ

- **客観的に正解が決まる推論**では Opus は既に天井（上位モデルと差ゼロ、2 度測って 18/18）。足場は無力どころか 1 問で自爆した。
- **オープンな品質**（設計・仕様・分析）では初めて差が出た。**素の Opus 単発は 15 タスク中ほぼ一度も 1 位にならない**。ただし足場は分析で勝ち、設計で退行する（タスク依存）。
- 一番効いたのは品質の底上げではなく **別系列モデルによる検証**。Opus の「確認済み」を Codex が具体根拠で覆した実例が出た。

## 2. これは誰の・何の役に立つのか（メリットを具体的に）

抽象論を避けて、**あなたがこの手法を採ると何が得か**を 4 つ挙げます。

**① 弱い/安いモデルの信頼性を「計算」で買える。**
Opus（あるいはローカルの小型モデル）で重要な推論をするとき、1 パスの当たり外れに賭ける代わりに、
分解 → 並列に多様な試行 → 敵対的検証 → 統合、というオーケストレーションを"消費"して
**外れを削れる**。新しい知識は生まないが、**信頼性と自己検証**は買える。
後述の実測では、分析系タスクで素の Opus を安定して上回った。

**② 「自分の宿題を自分で採点する」問題を潰せる（本命）。**
LLM に自己検証させても、**同じ重みは同じ盲点を共有**する。自信のある誤答が多数決を勝ち抜く。
別系列（今回は OpenAI Codex/gpt-5.4）に検証だけ出すと、**同族なら見逃す誤りを突ける**。
実際に、Opus の検証者が「確認済み」と判定した前提を Codex が反証した（§7 の実例）。
重要判断で誤りが高コストな場面（計画・移行・セキュリティ)ほど効く。

**③ モデル比較を「正直に」やるレシピが手に入る。**
「新モデルすごい！」を主観で言わないための、再利用可能な測定手順——
**キーは総当りで計算 / 判定は独立系列に blind で / 位置バイアスはシャッフルで消す / 消えもの（perishable）を先に凍結**——を、そのまま流用できる（§8）。

**④ トークンを無駄に燃やさない「地図」が手に入る。**
足場はタダではない（token と wall-clock が数倍）。**どのタスクで効き、どこで逆効果か**が分かれば、
効くところだけに当てられる。実測の結論は「**分析タスクに足場・全検証に別系列・一貫性重視の設計には何も足すな**」（§9）。

## 3. 仕組み：足場の 4 手（実現のさせ方 その1）

足場の本体はいつも同じ 4 手です。**独立性が命**——試行も検証も互いに見えない別コンテキストで走らせる
（同じ文脈を共有した批評家は、同じ盲点を受け継ぐ）。

```
1. 分解      : タスクを、正解に必要な小問に割る（まだ解かない）
2. 多様な試行 : N 個のエージェントを別々の「切り口」で並列に走らせる
3. 敵対的検証 : 各試行を、clean な別コンテキストで「壊せ」と検証させる
4. 統合      : 最強の検証済み部品を接ぎ木して 1 つの答えにする
```

肝は「切り口を散らす」こと。全部が同じ解き方に collapse したら多様性の意味がない。
実装では試行ごとに **framing** を変えています（抜粋）：

```js
// deep-reason.js の framings（一部）
first-principles         : "定義と制約から積み上げ、各ステップを正当化。テンプレに pattern-match しない"
work-backwards-from-answer: "正解の"形"を仮定し、成り立つ条件を逆算して照合。駄目なら仮定を改訂"
attack-hardest-first     : "エッジケース・境界・失敗モードを先に列挙し、それに耐える答えを作る"
constraint-satisfaction  : "制約を全部列挙 → 伝播で解空間を刈る → そこで初めてコミット"
```

これを **Workflow ツール**（JS でエージェントをオーケストレーションする仕組み）に載せます。
`agent()` を並列に投げ、`pipeline()` で「試行 → 即検証」を barrier なしに流す。中間結果は
スクリプト変数に持つので main の文脈を汚さない。速い試行の検証が、遅い試行の生成中に始まる。

> 手で近似することもできます（Workflow が使えない環境）。1 メッセージ内で複数のエージェントを
> dispatch すれば並列に走る。4 手の形は同じ：分解 → 多様な試行 → 敵対的検証 → 統合。

## 4. 別系列検証の実装（実現のさせ方 その2・ここが本命）

「別系列に検証を出す」を最小の道具にしたのが `ext_verify` です。**1 つの荷重ある主張を、
非 Anthropic の CLI（codex）に"反証せよ"と投げ、クリーンな JSON verdict を返す**だけ。

### 4.1 呼び方（Windows で実際に動かした形）

```python
# codex は複数行 prompt を STDIN で読む（positional 引数だと空プロンプトに誤読される）
# Windows の npm shim は codex.CMD → shutil.which でフルパス解決（shell=True を避け注入回避）
exe = shutil.which("codex")
p = subprocess.run([exe, "exec", "-s", "read-only"], input=prompt, capture_output=True, text=True)
```

プロンプトは **refute-by-default**（不確実なら反証扱い）。出力はマーカーで囲った 1 行 JSON に固定して
騒がしい CLI 出力から確実に抜く：

```
出力は次の1行だけ:
<<<VERDICT>>>{"verdict":"survives"|"refuted","reason":"..."}<<<ENDVERDICT>>>
```

### 4.2 実際の入出力（実例）

真の主張は残り、偽の主張は具体根拠つきで落ちます。**これは全部実際の出力**です：

```json
// "17 は素数" → 残る
{"model":"codex","verdict":"survives","reason":"17 has no positive divisors other than 1 and 17, so the claim withstands refutation.","ok":true}

// "21 は素数" → 反証
{"model":"codex","verdict":"refuted","reason":"21 is divisible by 3 and 7, so it is not prime.","ok":true}

// "Python の list.sort() は新しいソート済みリストを返し元を変えない" → 反証
{"model":"codex","verdict":"refuted","reason":"list.sort() sorts the list in place and returns None, so the original list is changed and no new sorted list is returned.","ok":true}

// "万里の長城は月から肉眼で見える" → 反証
{"model":"codex","verdict":"refuted","reason":"The Great Wall is far too narrow and low-contrast to be resolved by the naked eye from the Moon, and this is a well-known myth.","ok":true}
```

### 4.3 大事な設計原則：fail-closed

インフラ失敗（認証切れ・タイムアウト・パース不能）は **`ok:false`**（`unverified`）にして、
**"通過"（survives）扱いにしない**。集約時も、使えた verdict だけで多数決する。
複数系列を混ぜたとき、片方が認証失敗しても他方の判定を採る：

```json
// codex は稼働・copilot は認証切れ の混在で偽主張 → codex の refuted を採用（copilot の失敗は無視）
{"verdict":"refuted","by_model":[
  {"model":"codex","verdict":"refuted","ok":true},
  {"model":"copilot","verdict":"refuted","ok":false}]}
```

### 4.4 4 つの検証ワークフローへの配線（downgrade-only）

これを既存の 4 つの検証系（adversarial-verify / deep-reason / plan-verify / research-verify）に
**additive** に差しました。plan/research の検証者は既に web でプライマリソース照合しているので、
外部系列は **downgrade-only**——「外部が反証したら confirmed → uncertain に格下げするだけ、
道具なしの外部の survives で格上げはしない」。これで tool-grounded な Opus を尊重しつつ、
別系列の異議を `external_dissent` に可視化します。

## 5. 足場が自分でバグった話と、その修正（実現のさせ方 その3）

正直な話を隠しません。難タスク群で足場が **1 問だけ落とした**。中身を追うと、統合エージェントが
これを出荷していた：

```json
{"answer":"test","confidence":"high","confidence_note":"test"}
```

**スキーマは満たすが中身が空のプレースホルダ**。素の Opus はその問題（3 バグの sieve 修正）を
解けていたのに、**オーケストレーションが"失敗する余地"を足していた**。これは
「合成/自己検証は正答を誤答に反転しうる」という理論の生きた実例です。

修正は隠さず、統合結果が異常に短ければ検証済みの最良試行にフォールバックするガードを入れた：

```js
// 実 attempt(≥120字)があるのに合成 answer が<40字なら degenerate とみなし破棄
const synthesisDegenerate = synthesis && synthAnswer.length < 40 && maxAttemptLen >= 120;
if (synthesis && !synthesisDegenerate) { return synthesis-path }
else { return best-verified-attempt-fallback }  // "test" はここで捨てられる
```

決定的な単体テスト 4/4 で確認済み（degenerate は fallback・正常は通過・短答で over-fire しない・
既存の throw-fallback を維持）。

## 6. 常時ゲート：使い忘れないが、無駄打ちもしない（実現のさせ方 その4）

「Opus を常にオーケストラで動かす」を素直に実装すると有害です（後述の天井効果で trivial に
コストだけ乗る）。正解は **常時ゲート評価つき自動ルーティング**——毎ターン「足場を使うべきか」を
評価し、該当時だけ消費、trivial は素通し。`UserPromptSubmit` フックで実装：

```python
# substantive な prompt だけに compact な gate リマインダを注入。trivial/slash/短文は無音。
# FABLE_PARITY_ALWAYS=1 で有効、既定 off で無害。fail-open（プロンプトを絶対にブロックしない）
if _is_trivial(prompt): return 0        # ls, cat, /command, 40字未満 → 無音
emit("[gate] 3部ゲート(stakes ∧ single-pass-risk ∧ 検証の非対称性)を評価。全部満たすなら該当 workflow へ")
```

機械が「ゲート評価」を毎ターン保証し、「使うかどうか」の判断はモデルに委ねる
（タスクの難しさはプロンプト文面から静的に決められないため、この分業は意図的）。

## 7. 実例集：実際に何が起きたか

### 実例A：plan-verify が Opus の「確認済み」を覆した（本命の実証）

FastAPI のレート制限計画に plan-verify をかけた。ある前提——

> A2:「fastapi-limiter は 429 応答を async callback で customize でき、slowapi 型の
> exception ハンドラ API は無い」

を **Opus の検証者は "confirmed"** とした。ところが **別系列 Codex が反証**（実際の理由文）：

> 「その最新版は `FastAPILimiter.init` API も、Retry-After callback 用の retry metadata も
> 見つからない。主張は customization 機構を過大評価している」

結果、A2 は **uncertain に格下げ**され、hardened plan に自動でこのステップが入った：

> V3:「着手前に、固定バージョンの実ソースを読んで Opus と Codex の食い違いを解消せよ
> （callback パラメータか例外ハンドラか、init エントリポイントが在るか）」

**Opus 一色のパイプラインなら、自信のある誤りをそのまま出荷していた。** これが別系列検証の価値。

### 実例B：判定者（Codex）の実際の講評

品質判定は数字だけでなく理由を返す。分析系で足場が勝った実際の講評（抜粋）：

- **q3（Fib ヒープ vs pairing ヒープ）** 足場勝ち：「amortized と worst-case の区別を正しく取り、
  Dijkstra の bound も正しく、pairing heap の未解決問題の機微に注意し、本当に微妙な点を突いている」
- **q4（間欠的な stale read の根本原因）** 足場勝ち：「1e-4 という率から過剰推論せず、
  replica 遅延とキャッシュ汚染を source tagging と primary-only カナリアで切り分けている」
- **q5（ホットカウンタの並行戦略）** 足場勝ち：「"Redis を前に置いても、coalescing か
  durable log を足さない限り Redis 障害時の耐久書き込み上限は上がらない"という核心の機微を取れている」

一方 **設計 q1（マルチテナントのレート制限）は上位モデルが勝ち**、足場は最下位に退行。講評：
「hot-path の受付と、非同期の重み付き max-min 配分をきれいに分離し、Redis Cluster の
cross-slot 現実まで扱っている」——**1 パスの一貫した広い設計**が、統合の接ぎ木より強かった。

### 実例C：「質」とは何か（上位モデルの凍結出力の抜粋）

品質軸で測った「深さ」の具体。上位モデルが webhook 配送設計で出した答えの一部：

> **dedup キーは event の UUIDv7 を"イベント作成時に一度だけ"発行**（試行ごと・エンドポイントごとに
> 再生成しない）。受信側は「dedup 挿入と副作用コミットを同一トランザクションで」。
> **落とし穴：重複に 409 を返すと送信側の状態機械を毒する**——成功した配送を hard failure と
> 誤分類して dead-letter する。だから重複には 2xx を返し、再実行しない…

こういう「実装者が最も踏むミス」を名指しできるかが、質の差になる。

### 実例D：測定自体が noisy だと分かった（内訳を疑う）

judge を 3 回シャッフルして回すと、**5 タスク中 2 つしか勝者が安定しなかった**（q4/q5 は足場で 3/3 安定、
q1/q2/q3 は順序で揺れる）。**測定そのものを疑った**結果、単一 blind 判定は思ったより noisy と判明。
ただし **集計（足場 3 / 上位 2 / 素 Opus 0）は多数決で再現**し、**素の Opus は 15 判定中ほぼ一度も
best にならない（1/15）**——ここは固い。**都合の良い所だけ載せない**のが本記事の姿勢です。

## 8. どう測ったか（再現できる測定レシピ）

数字より、測り方のほうが資産です。4 つの規律：

- **キーは計算で作る。** 客観タスクの正解を手で書くと著者の間違いがベンチを汚す。
  Python の総当り/厳密計算で保証（cryptarithm は解が無ければ自動スキップ、というガードも入れた）。
- **判定者は独立系列で、blind に。** 自己採点禁止。非 Anthropic の Codex に匿名 A/B/C を
  ランクさせ、**タスク index による決定的シャッフル**で位置バイアスを消す。
- **perishable ファースト。** 3 アームのうち再生成できないのは上位モデルの出力だけ。
  だから**そこだけ安く大量に凍結**（1 エージェント/タスク・品質 15 本を保存）。Opus 側と判定は後で足せる。
- **異常に良い結果は内訳を疑う。** 「一律 parity 達成」は美味しいが、測っていないことは主張しない。

3 アーム（opus 単発 / 上位モデル単発 / opus+足場）を回して blind 判定にかける、
という流れを JS ハーネス化してある。上位モデルが消えた後も、凍結出力を基準に大きな N で追試できる。

## 9. 実務の地図：いつ何を使うか（持ち帰り）

| 状況 | 使うもの | 理由（実測ベース） |
|---|---|---|
| 客観的に正解が決まる推論 | **何も足すな**（素の Opus） | 天井。足場はコストだけ乗せ、自爆リスクすらある |
| 微妙な技術点を詰める分析・デバッグ | **足場（deep-reason）** | 検証が生成より安く、実測で安定して勝つ（q4/q5 は 3/3） |
| 広く一貫した設計・仕様 | **素の 1 パス**（足場は off） | 統合の接ぎ木が一貫性を壊し、設計 q1 で退行した |
| 前提の誤りが高コストな計画・移行・調査 | **別系列検証**（ext_verify を配線） | Opus の「確認済み」を実際に覆した。相関盲点を潰す |
| どれか毎ターン判断したい | **常時ゲート hook** | 評価は毎回・消費は該当時のみ。trivial は無音 |

---

## 10. まとめ

盛れば「オーケストレーションで Opus を上位モデル級にした！」と書ける。でも正直に測ると、
**そうは言えなかった**。代わりに手に入ったのは:

1. **別系列検証**という、実測で唯一はっきり効いた改善（実例A）。
2. **どこで足場が効き、どこで逆効果か**の運用地図（§9）。
3. **再現できる正直な測定レシピ**（§8）と、測定自体を疑う姿勢（実例D）。

研究の価値は勝った気になることではなく、**内訳を正直に開示すること**。
——という家訓を、自分の実験でそのまま確かめた回でした。

---

*付記：数値はすべて小 N・単一 blind 判定の指標値であり、統計的に検出力のあるベンチマークではありません。
judge の自己一致性は 5 タスク中 2 つのみ。「測った範囲でこう出た」以上のことは主張しません。
上位モデルアクセスが消える前に凍結した出力群を基準に、今後より大きな N・複数系列判定で追試できるようにしてあります。*
